# Cirrus — Production Readiness TODO

Checklist to take Cirrus from "works in local Docker Compose" to "safe to run in production." Target deployment is the **existing Docker Compose + Traefik setup** (see `docker-compose.yml` — already has a real domain, `cirrus.example.com`, with Let's Encrypt TLS at the edge). This is a deliberate choice: `PRD.md` §8 names Kubernetes as the long-term target, but Compose+Traefik is what's actually wired up today, so it's the near-term production path — Kubernetes stays on the list below as roadmap, not a blocker.

See [ARCHITECTURE.md](ARCHITECTURE.md) for how the pieces fit together and [CLAUDE.md](CLAUDE.md) for the full incident/decision history behind the feature gaps in P4.

## P0 — Blockers (must fix before going live)

- [x] Real Microsoft Entra ID app registration obtained and wired into `.env` (`ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET`).
- [x] `DEV_LOGIN_ENABLED` now has a second, independent gate: `backend/auth/src/env.ts`'s `devLoginEnabled` also requires `NODE_ENV !== 'production'`, so a stray `DEV_LOGIN_ENABLED=true` left in a production `.env` can't reactivate `/dev-login` once deployed with `docker-compose.prod.yml` (which sets `NODE_ENV=production`). A suppressed-but-requested case now logs a distinct warning in `server.ts`.
- [x] Every insecure baked-in default in `docker-compose.yml` (`INTERNAL_SHARED_SECRET`, `COOKIE_SECRET`, `POSTGRES_PASSWORD`) now uses Compose's `${VAR:?message}` syntax (same pattern `VAULT_TOKEN` already used) — `docker compose up` now refuses to start if any of these are unset, instead of silently falling back to a dev value. `.env.example`'s example values for these were blanked out too, each with a `openssl rand -hex ...` generation hint, so there's nothing left to copy-paste into a real deployment.
- [x] Vault bootstrap fixed: `vault/entrypoint.sh` now writes unseal keys + root token to a dedicated `vault-init` Docker volume (`/vault/init`), separate from `vault-file` (`/vault/file`) where the encrypted secret data lives, and no longer `echo`s the raw `vault operator init` output to container logs on first boot. An already-running deployment self-migrates its existing `vault-file`-resident init file to the new volume on its next restart, no manual steps needed. Still needed as a one-time **manual** operational step: rotate/purge the root token + unseal keys already printed to this environment's *existing* `docker compose logs vault` output from a prior boot — code can't undo that.
- [x] Postgres/Redis/Vault no longer publish their ports to the host when deployed via the new `docker-compose.prod.yml` overlay (`ports: !reset []`) — `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build` is now the production invocation. Local dev keeps using the plain `docker compose up -d --build`, unchanged, with those ports still exposed for `psql`/`redis-cli`/`vault` CLI convenience.
- [x] `NODE_ENV=production` is now set for `bff`/`auth`/`rbac`/`aggregator` via `docker-compose.prod.yml`, and all four now register a `setErrorHandler` (`server.ts`) that logs the full error server-side but only ever sends a generic `"Internal Server Error"` message to the client for 5xx — intentional 4xx messages (validation, etc.) still pass through.
- [x] `restart: unless-stopped` added to all 14 services in `docker-compose.yml`.
- [x] Healthchecks added for `bff`, `frontend`, and all 5 collector services. Collectors run on `gcr.io/distroless/static-debian12:nonroot`, which has no shell/tools at all, so each collector Dockerfile now `COPY`s a statically-linked `busybox:1.36-musl` `wget` binary in alongside the app binary purely so Compose's `CMD`-form healthcheck has something to exec (verified: builds and runs fine, no missing-library errors). `aggregator`'s `depends_on` on the 5 collectors and `frontend`'s `depends_on` on `bff` were tightened from `service_started`/implicit to `service_healthy` now that there's a real check to wait on.

## P0.5 — MVP feature gaps (PRD promises not fully delivered)

Found via a direct code audit against `PRD.md` §4–§6 and the frontend's own UI completeness, separate from the infra/ops gaps above. Some of these are the same underlying issue already listed elsewhere (e.g. the health-check job also appears in P2) — kept here too since they're PRD-level functional gaps, not just ops nice-to-haves.

- [x] **Periodic connection health-check job (PRD §6.1/§7.3) — built.** `backend/rbac/src/scheduler.ts` runs an in-process `setInterval` (`HEALTH_CHECK_INTERVAL_SECONDS`, default 21600s/6h, 0 disables it) that re-checks every stored connection (all providers, all statuses) in batches of 5 via `Promise.allSettled`. The manual `POST /connections/:id/test` route's update+audit logic was extracted into `backend/rbac/src/lib/connectionCheck.ts`'s `runConnectionCheck()` so both paths share one code path; a new `metadata.source: 'manual' | 'scheduled'` field on the `connection_test` audit action distinguishes the two (no new "system actor" — `actorUserId: null` was already a supported value). Single-`rbac`-instance assumption, no jitter needed today. (Same item as P2's health-check bullet below.)
- [x] **Inventory filters — account/region added.** PRD §4.1.2/§5.3 promise filter by provider, account/project, region, and status. `useCirrusApp.ts` now has `filterAccounts`/`filterRegions` (and `InventoryScreen.tsx` two more `FilterDropdown`s) alongside the existing provider/status/search. Unlike provider/status (a fixed universe, seeded to "all"), account/region have no fixed universe — the option list is derived live from distinct `Vm.account`/`Vm.region` values as VMs stream in — so these two use `[] = unrestricted` semantics instead of a pre-seeded full list, so a newly-streamed-in account/region isn't incorrectly treated as filtered out.
- [x] **Users screen empty state — built.** `UsersScreen.tsx` now computes `showEmpty = usersRows.length === 0` and renders a real `EmptyState` (new `UsersOffIcon` added to `EmptyState.tsx`, matching `SearchOffIcon`/`LinkOffIcon`'s style) with a "+ Invite User" `action` (reusing `app.openInviteUser()`, same handler as `UsersHeader`'s existing button) instead of the table when there are no users — following Inventory's pattern of rendering `EmptyState` directly inside the existing `.card` wrapper, not Connections' extra duplicate-styled wrapper div.
- [x] **Real "fetch failed" state — built.** `useCirrusApp.ts` now tracks `connectionsError`/`usersError`/`vmsLoadError` (all `string | null`) alongside `connections`/`users`/`vms`, set in the same `.catch` blocks that already `showToast` on a load failure (which now also correctly passes the `'error'` toast variant — previously omitted, so failure toasts rendered with success styling) and cleared on the next successful load. `loadConnections()`/`loadUsers()` were extracted out of the bootstrap effect so a "Retry" action can re-run them, not just once at mount; Inventory reuses the existing `refreshInventory()` as its retry action. Each of the 3 screens now renders a distinct error branch (new `AlertTriangleIcon` in `EmptyState.tsx`, `stroke="var(--error-border)"` — a CSS var that existed but was unused until now) *before* the normal empty-state branch, gated on `error != null && rows.length === 0`, so a failed fetch no longer shows the "+ Add Connection"/"+ Invite User"/"No VMs match your filters" copy — it shows the actual error message plus a "Retry" button instead.
- [x] **Client-side form validation — built.** New `frontend/src/lib/formValidation.ts` holds pure `validateUserForm` (name required, email required + basic format regex) and `validateConnectionFields` (account name + every non-`generated` `FieldDef` required — `FieldDef` carries no `required`/format metadata from the backend, so every visible field is treated as required by default). `useCirrusApp.ts`'s `saveUser`/`runTest`/`saveEditConnection` each validate first and `return` before calling the API if any errors exist, populating new `userFormErrors`/`wizardFormErrors`/`editFormErrors` state (cleared on next successful submit, on drawer/wizard open-close-step-change, and per-field the moment its value changes again); `runEditTest` is deliberately untouched — it re-tests the already-persisted connection via `testConnection(id)`, not the unsaved form values, so field validation doesn't apply to it. `CredentialFieldRow` (`shared/CredentialField.tsx`) gained an optional `error?: string` prop rendered inline (`var(--error-border)`, matching `AlertTriangleIcon`'s color); `UserDrawer.tsx`/`WizardScreen.tsx`/`EditConnectionDrawer.tsx` wire their respective error maps into it (plus the account-name/name/email plain `<input>`s, which don't go through `CredentialFieldRow`). Edit-drawer validation passes `allowMaskedSecret: true` so an untouched `MASKED_PLACEHOLDER` secret field (already-set, not re-entered) is correctly treated as valid rather than required-but-empty.
- [x] **iOS Safari safe-area fix now applied to all four drawers.** Rather than duplicating Sidebar's per-component inline-style fix (`d4ca68f`), the bottom padding on the shared `.drawer-panel` class in `frontend/src/index.css` (used exclusively by `UserDrawer.tsx`/`EditConnectionDrawer.tsx`/`VmDetailDrawer.tsx`) now adds `env(safe-area-inset-bottom)` to its existing bottom padding, both in the base rule and the `@media (max-width: 640px)` override — covers each drawer's bottom action row automatically with no per-component change needed.
- [x] **Loading state added for Connections/Users.** `useCirrusApp.ts` gained `connectionsLoading`/`usersLoading` (default `true`, flipped `false` in a `.finally()` on `loadConnections`/`loadUsers`, mirroring `isLoadingVms`). New `ConnectionCardSkeleton.tsx`/`UserRowSkeleton.tsx` (own chip-placeholder markup wrapped in `<phantom-ui loading>`, matching `SkeletonRows.tsx`'s existing pattern rather than reusing it directly, since the card-grid and 3-column-table shapes differ from Inventory's 10-column table) render in a new `showLoading` branch inserted before the existing error/empty checks in `ConnectionsScreen.tsx`/`UsersScreen.tsx`, each gated on `!showLoading` so all four states (loading/error/empty/normal) stay mutually exclusive.

## P1 — Security hardening

- [x] **Explicit CORS policy on `bff` — built.** `@fastify/cors` registered in `server.ts` (`origin: env.corsOrigin, credentials: true`, first plugin registered) with a new `CORS_ORIGIN` env var (default `http://localhost:5173`, set to the real public URL in production) — see `CLAUDE.md`'s Backend section for detail.
- [x] **Rate limiting — built.** `@fastify/rate-limit` on `auth` (per-route `global: false`, only `/login`/`/dev-login`, shared `RATE_LIMIT_LOGIN_MAX`/`RATE_LIMIT_LOGIN_WINDOW_SECONDS` budget) and on `bff` (global, `RATE_LIMIT_API_MAX`/`RATE_LIMIT_API_WINDOW_SECONDS`, `/health` exempted). Both Fastify instances also gained `trustProxy: true` — see `CLAUDE.md`'s Backend section for why that's a required companion change, not optional.
- [x] **Security headers — built.** `@fastify/helmet` on all 4 backend services (CSP disabled — meaningless for a JSON API, see `CLAUDE.md`) plus a hand-written CSP/HSTS/X-Frame-Options/etc. header set in `frontend/nginx.conf`'s `server {}` block (the one origin that actually serves the SPA document). CSP's `style-src 'unsafe-inline'` is deliberate, not an oversight — see `CLAUDE.md`'s Backend section for why. Verified live via Playwright against the real deployment; also surfaced a pre-existing, unrelated Connections-screen crash (not CSP-caused, not fixed here).
- [x] **Log redaction + `LOG_LEVEL` — built.** All 4 backend services now build `Fastify({ logger: { level: env.logLevel, redact: logRedactPaths }, ... })` instead of the bare `logger: true` — precautionary (confirmed no active leak today, see `CLAUDE.md`'s Backend section), covers headers/cookies/session-JWT-shaped keys. `LOG_LEVEL` env var wired through `.env.example`/`docker-compose.yml`, default `info` (no-op unless overridden). Verified live: `LOG_LEVEL=warn` suppresses info-level request logging.
- [x] **Internal TLS — decided: accept the risk, documented, not built.** Confirmed the whole mesh (`bff`/`auth`/`rbac`/`aggregator`/5 collectors/`postgres`/`redis`/`vault`) sits on one flat single-host Docker bridge network — Traefik only ever touches `frontend`. A Traefik-cert-reuse idea was raised and ruled out (public Let's Encrypt cert can't cover the internal `vault` hostname, and the cert isn't accessible outside Traefik's own external config anyway); the real alternative (a self-signed internal CA, HashiCorp's own recommended pattern for Vault) is real ongoing PKI work judged disproportionate for this deployment shape. See `CLAUDE.md`'s Backend section for the full reasoning — revisit if the deployment ever goes multi-host or a compliance requirement appears.
- [x] **Backup procedure — built.** New `postgres-backup`/`vault-backup` sidecar services (`docker-compose.yml`, scripts in `backup/`) — daily gzipped `pg_dump` and a read-only tar of `vault-file`, both pruned to 1 week by default, written to a host-visible `./backups/` (gitignored). `vault-init` (unseal keys/root token) is deliberately never backed up — see `CLAUDE.md`'s Backend section for why that satisfies "decoupled from wherever the unseal keys end up." Verified live: both backups validated, a real Postgres restore recovered actual row counts, and retention pruning confirmed.
- [x] **Log size caps — built.** One `x-logging: &default-logging` anchor (`max-size: "10m"`, `max-file: "3"`) referenced via `logging: *default-logging` on all 16 services in `docker-compose.yml`, instead of duplicating the block per-service. Verified live via `docker inspect`'s `HostConfig.LogConfig` on every running container.
- [ ] Add `deploy.resources` (cpu/mem) limits per service — none exist today, so one runaway container (e.g. a collector stuck in a retry loop) could starve the host.
