## Frontend (`frontend/`)

- Tech stack matches PRD §8: React + TypeScript + Vite; `oxlint` for linting (`npm run lint`); `tsc -b && vite build` for the build.
- State: a single `useCirrusApp()` hook (`src/state/useCirrusApp.ts`) holds all app state/actions — no external state library (Redux/Zustand etc.). Keep new state co-located there rather than introducing a second state mechanism.
- Styling: CSS variables per theme + component classes in `src/index.css`, not inline style-string builders (that was the source mockup's approach, deliberately not carried over). Dynamic/data-driven colors (provider brand colors, status colors) stay as inline `style`.
- Theme default: light mode, set via the initial `useState<Theme>('light')` in `src/state/useCirrusApp.ts`. There's no persistence or OS-preference (`prefers-color-scheme`) detection — theme choice is in-memory only and resets to light on reload.
- Data: no more mock data file — `src/api/client.ts` holds typed fetch wrappers for every BFF route, and `src/state/useCirrusApp.ts` is fetch-driven (bootstraps the session via `GET /auth/me`, then loads `providers`/`vms`/`connections`/`users` from the backend; `providers` now carries `fieldDefs`/`setupGuide`/`failureMessage` per-provider, replacing the old static `FIELD_DEFS`/`CHECKLIST`/`FAILURE_MSG` maps from PRD §7.3 — the wizard step-2 side card renders `setupGuide` under the heading "How to get these values", provider-specific instructions for obtaining the credential values from each provider's own console, not a list of API calls Cirrus makes to verify them). Always fetch relative paths (`/api/...`, `/auth/...`), never an absolute `localhost:8080` URL — both the Vite dev server (`vite.config.ts`'s `server.proxy`) and the built container's nginx (`nginx.conf`) proxy those same relative paths to the BFF, so the identical bundle works unmodified in either mode. The two run on the same host port (5173) by convention — never both at once.
- Routing is real, not a `screen`-state switch: `src/router.tsx` defines a code-based TanStack Router (`@tanstack/react-router`) route tree — `/` (login, redirects to `/inventory` if already authenticated), and a protected layout route (redirects to `/` if not authenticated) with children `/inventory`, `/connections`, `/connections/new` (the add-connection wizard), `/users` (the latter three additionally guarded admin-only via `beforeLoad`, mirroring `Sidebar.tsx`'s nav-item visibility but enforced even on a direct URL visit). `App.tsx` still calls `useCirrusApp()` once and only mounts `<RouterProvider router={router} context={{ app }} />` after `authChecked` — this defers every route guard until the async session check resolves, avoiding a race, and is the documented TanStack pattern for injecting hook-derived context into a router created once at module scope. `useCirrusApp.ts` no longer holds a `screen` state at all; navigation goes through `router.navigate(...)` (confirmed via Context7 to work imperatively from a plain hook, not just inside components) or `<Link>` (used in `Sidebar.tsx`, with `activeProps` driving the nav-item highlight that `screen === X` checks used to do). `AppShell.tsx` is now just `ProtectedLayout` (Sidebar + an `<Outlet/>`) plus a small `ScreenLayout` helper each route's page component wraps itself in — a single `<Outlet/>` can only render one matched component, so header+body per screen can no longer be split across two containers the way the old `screen`-switch did.
- **`context={{ app }}` on `RouterProvider` is for `beforeLoad` guards only, never for rendering** — this was a real bug, not a hypothetical: route page components originally read the live `app` via `xxxRoute.useRouteContext()`, but TanStack Router only recomputes route context on a fresh match (navigation or `router.invalidate()`), so it doesn't reactively pick up state changes from clicks between navigations — confirmed via Context7 against TanStack's own docs/GitHub issues. Symptom was silent: clicking "Invite User" or a Connection card did nothing, yet the state change *had* happened — navigating away and back would reveal a drawer that was already open. Fixed by adding `src/state/AppContext.tsx` (a plain `createContext`/`useApp()` pair), providing it in `App.tsx` via `<AppContext.Provider value={app}>` wrapping `<RouterProvider>`, and switching every route page component plus `ProtectedLayout` from `useRouteContext()` to `useApp()` for rendering. `beforeLoad`/`requireAdmin` still correctly read `context.app` — that per-navigation guard use was never broken. If a new route page component is added, give it `useApp()`, not `useRouteContext()`.
- The Sidebar's old "Preview role" toggle, Inventory's old "Preview" (loading/empty/outage) toggle, and Connections' old "Preview: Default/Empty" toggle are all gone by design, not an oversight — once role and fetch state are server-driven, a client-side override of any of them would just lie to the user. Don't re-add them; if a design-preview mode is needed again, it should be a clearly-labeled dev-only affordance (see the `import.meta.env.DEV`-gated "Dev login" button in `LoginScreen.tsx` for the pattern), not a first-class UI control.
- Inventory's "Providers connected" stat card (`InventoryScreen.tsx`'s `stats` useMemo) counts `connections.filter(c => c.status === 'active').length`, not `providers.length` — `providers` is the static 5-entry provider-*type* catalog from `GET /api/providers` (used for the Add-connection wizard's field defs), never the live `cloud_connections` state, so counting it would always show 5 regardless of how many connections actually exist.
- Provider icons are bundled locally under `src/assets/providers/` (not hotlinked). Note for future icon updates: brandfetch's CDN blocks hotlinking without browser-like `User-Agent`/`Referer` headers on `curl`.
- `Toast` (`src/components/shared/Toast.tsx`) is self-animating, not parent-mounted/unmounted: it owns its own `phase` (`'entering' | 'exiting' | null`) state, so when `app.toast` clears it animates out (slide+fade, `toastOut` keyframe) for 200ms before actually unmounting, instead of vanishing instantly. Positioned top-right (`top: 88px; right: 24px` in `index.css`), offset below the 72px per-screen header row so it doesn't overlap header action buttons (Invite User, Add Connection, etc.) — it used to be bottom-center with no animation.
- Docker: `frontend/Dockerfile` is a multi-stage build (`node:24-alpine` → `nginx:stable-alpine`) per PRD §7's "Docker for dev" — keep base images current stable/LTS when touched, don't quietly pin to whatever the scaffold generated. It's wired into the root `docker-compose.yml` as the `frontend` service (port `5173:80`, `depends_on: bff`).

## Backend (`backend/`)

- npm workspaces monorepo: `shared-types` (mirrors `frontend/src/types.ts` — keep these in sync, it's the frontend-facing contract), plus `bff`, `auth`, `rbac`, `aggregator` — all Fastify services in TypeScript, run via `tsx` in dev and compiled (`tsc -b`) in their Docker images.
- `collectors/` is a *separate* Go workspace (`go.work`, not part of the npm workspace): `internal-kit` (shared HTTP envelope and RBAC-config-fetch helpers only — `rbacclient.go`'s `GetConnectionConfig` is used identically by every real collector, but carries zero provider-specific logic itself; the old deterministic fake-fleet generator (`stub.go`) from before every collector made real API calls has been deleted — no dead stub-generation code left) plus one independent module per provider (`aws/`, `gcp/`, `alibaba/`, `oci/`, `biznet/`) — each its own binary/container so a failure or bad release in one never affects the others (PRD §7.1's isolation goal).
- Service ownership boundaries: `rbac` is the *sole* owner of PostgreSQL (users, cloud connections, audit log — schema in `rbac/src/db/schema.ts`, Drizzle ORM); `aggregator` is the *sole* owner of Redis (per-`(provider, connectionId)` cache with a `SET NX PX` stampede lock, `aggregator/src/cache/lock.ts`); `bff` is the only service meant to be called from outside the Docker network and proxies/aggregates the others.
- Auth is real, not stubbed: `auth/` performs actual Microsoft Entra ID OIDC (Authorization Code + PKCE via `@azure/msal-node`), single-tenant, identity keyed on `oid`+`tid` per PRD §3. It mints its own ES256 JWT (via `jose`) and exposes a JWKS endpoint (`/.well-known/jwks.json`) that `bff` verifies sessions against. Needs real Entra ID app registration values (`ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET`) in `.env` — everything else in the stack works without them.
- Temporary dev-login bypass: `auth/src/routes/devLogin.ts` (`GET /dev-login?email=...`) logs in as any already-invited RBAC user without a real Entra ID redirect, gated by `DEV_LOGIN_ENABLED` (default off — never enable outside local dev). It reuses the same `RBAC /internal/upsert-on-login` call the real callback makes, so it can't invite/bypass RBAC, only skip the Microsoft redirect. `LoginScreen.tsx` surfaces it as an `import.meta.env.DEV`-only button, so it never ships in a production build. Delete this once Entra ID is fully wired up.
- Provider Collectors each expose the uniform `GET /instances?connectionId=...` contract from PRD §7.1, resolving their own connection config via a new RBAC internal endpoint (`GET /internal/connections/:id`, `rbac/src/routes/internal.ts`) — the Aggregator never sees or forwards credential material. **AWS** (`collectors/aws/`) uses a per-connection static IAM user Access Key (`accessKeyId`/`secretAccessKey`, no hub account or role assumption — `buildAWSConfig` in `internal/instances.go` builds an `aws.Config` directly from the connection's own credentials via `credentials.NewStaticCredentialsProvider`, fresh per request, mirroring OCI's `buildConfigProvider` pattern), then calls EC2 across every enabled region — **EC2 only, not Lightsail**: `AmazonEC2ReadOnlyAccess` (the policy suggested in the setup guide) doesn't grant any `lightsail:*` actions either, so a company VM running on Lightsail rather than EC2 simply won't appear in inventory today (PRD §11 item 6). **Alibaba Cloud** (`collectors/alibaba/`) does the RAM-role equivalent (`ALIBABA_CLOUD_ACCESS_KEY_ID`/`_SECRET`) against ECS. **GCP** (`collectors/gcp/`) uses real Workload Identity Federation — no static secret at all — via a new Auth Service capability (`POST /internal/wif-token`, `auth/src/routes/wif.ts` + `signWifToken()` in `auth/src/jwt.ts`, sharing the same signing key/JWKS as session tokens) exchanged through `golang.org/x/oauth2/google/externalaccount` against Google's real STS/IAM Credentials APIs, then Compute Engine. **OCI** (`collectors/oci/`) uses an API Signing Key (`common.NewRawConfigurationProvider` from `oci-go-sdk/v65`, per-connection `tenancyOcid`/`userOcid`/`fingerprint`/`privateKey`/`region`/`passphrase`), recurses every accessible compartment (`identity.ListCompartments` with `AccessLevel: Accessible`) and fans out `core.ListInstances` + boot/block volume (`blockstorage`) + VNIC (`core.ListVnicAttachments`/`GetVnic`) lookups per compartment to build full instance records. **Biznet Gio** (`collectors/biznet/`) has no official SDK, so it's a plain REST client against `api.portal.biznetgio.com` with an `x-token` header, fanning out in parallel to both the NEO Lite and NEO Lite Pro product lines (`/neolites/accounts`, `/neolite-pros/accounts`) and tolerating one line failing as long as the other succeeds; because Biznet's real OpenAPI spec declares empty response schemas for every endpoint, field extraction is deliberately defensive (`extractField`'s candidate-key lookup) rather than a confident fixed struct. None of the 5 collectors has been tested against a real successful fetch (no real Alibaba hub credential, real AWS IAM user, GCP resources, or OCI/Biznet accounts exist yet) — only that they compile against the real SDKs and fail gracefully (`AUTH_FAILED`/`UPSTREAM_ERROR`) when given fake credentials; AWS/GCP were observed reaching real STS/IMDS endpoints, and OCI/Biznet were observed reaching OCI's real Identity API (genuine 401) and Biznet's real Portal API (genuine 400) respectively. Collector/Aggregator timeouts were raised accordingly (5s stub-era budget → 20s AWS / 10s Alibaba / 15s GCP / 20s OCI / 15s Biznet per collector, 25s at the Aggregator, `aggregator/src/cache/lock.ts`).
- `POST /api/connections/:id/test` (in `rbac`) is real, not simulated: each of the 5 collectors now also exposes a lightweight `GET /test?connectionId=...` (own timeout budget, much smaller than the full fetch — 8s AWS / 6s Alibaba / 10s GCP / 6s OCI / 5s Biznet — split out of the collector's single outer `WithTimeout` wrap so `/instances` keeps its own larger budget) that performs only the cheapest authenticated call per provider: AWS `sts:GetCallerIdentity`+`ec2:DescribeRegions` against the connection's own static IAM Access Key; Alibaba `sts:GetCallerIdentity` only (no ECS call, still via AssumeRole); GCP the WIF exchange itself plus `resourcemanager.testIamPermissions` (needs a second, more broadly-scoped `cloud-platform.read-only` token source than the full fetch's `compute.readonly` one — see `buildTestTokenSource` in `gcp/internal/wif.go`); OCI `identity.ListRegions` + `core.ListInstances` limited to 1 result on the tenancy root compartment only (no compartment recursion); Biznet a single `GET /neolites/accounts`. Each provider's credential-building logic was factored out of its `FetchInstances`/`GenerateInstances` (e.g. `buildAWSConfig` in AWS, `buildAssumedCredential` in Alibaba) so the full fetch and the lightweight test share it rather than duplicating it. RBAC calls these via a new `rbac/src/lib/collectorClient.ts` (plain `fetch` + `AbortController`, mirroring the Aggregator's own `fetchFromCollector` in `aggregator/src/cache/lock.ts`) and a new `COLLECTOR_URLS` env-var block in `rbac/src/env.ts` — RBAC does NOT depend_on the collectors in `docker-compose.yml` (would create a cycle, since every collector already depends_on rbac); a collector being down at test time is classified as `UPSTREAM_ERROR`, distinct from a real credential rejection. The frontend's wizard-only "Simulate: Success/Failure" pill (a dev-era artifact for the old stubbed route) is gone along with `testConnection`'s `simulate` param, same category as the earlier-removed Sidebar/Inventory preview toggles. Verified live: real per-provider SDK/network calls observed reaching AWS STS/IMDS, GCP's IAM Credentials API, OCI's Identity API, and Biznet's Portal API with fake credentials, each producing a specific real rejection message (not a canned string) persisted to `cloud_connections.last_check_message` and audited; a stopped collector container is classified gracefully as `UPSTREAM_ERROR` rather than hanging. **Not yet built: the periodic background re-validation job** PRD §6.1/§5(step 7)/§7.3 call for (recommended every 6h, re-running this same lightweight per-provider check against every stored connection and updating its status automatically) — today `testConnectionViaCollector`/`collectorClient.ts` is only ever invoked synchronously from this manual on-demand endpoint. There's no cron/scheduler package installed, no timer in any service, and no dedicated scheduler container in `docker-compose.yml` — a connection that goes bad after its last manual test will show stale `Active` status until an Admin re-tests it or a user hits an error.
- Vault is real, not deferred, and runs in **production mode** (not dev mode — switched after a real incident where a live AWS connection's `secretAccessKey` was silently lost on a `vault` container restart, since dev mode is in-memory only): the `vault` service (`hashicorp/vault`) boots via a custom `vault/entrypoint.sh` (bind-mounted, replaces `command: server -dev`) that starts `vault server -config=/vault/config/config.hcl` (`vault/config.hcl` — `storage "file"` at `/vault/file`, backed by the `vault-file` named Docker volume so it persists across restarts like `pgdata` does; `disable_mlock = true` since the custom entrypoint bypasses the image's own root→vault `setcap cap_ipc_lock` step; `listener "tcp" { tls_disable = 1 }`, consistent with every other inter-service call in this stack being plain HTTP inside the Docker network). On first boot the entrypoint runs `vault operator init` (5 Shamir key shares / 3 threshold) and persists the unseal keys + initial root token into `/vault/file/.cirrus-init/init.txt` — inside the same volume Vault's own data lives in, so both survive or are lost together — and on *every* boot (first or not) it re-unseals from that file, enables the `secret/` KV v2 mount, writes a least-privilege `cirrus-rbac` policy (`secret/data/cirrus/connections/*` create/read/update/delete, `secret/metadata/cirrus/connections/*` delete), and mints RBAC's actual token pinned to the `VAULT_TOKEN` value from `.env` (passed into the vault container as `CIRRUS_RBAC_TOKEN`, deliberately not `VAULT_TOKEN`, so the vault CLI doesn't try to auth with a token that doesn't exist yet) — no renewal job, `-ttl=87600h` (~10 years), same operational shape as this project's other long-lived static secrets (`INTERNAL_SHARED_SECRET`). `vault/healthcheck.sh` gates the Docker healthcheck on a bootstrap sentinel file, not just `vault status`, so `rbac` (which `depends_on: vault: condition: service_healthy`) never starts against a half-provisioned Vault. This backs `rbac/src/lib/vault.ts`, the *only* Vault client in this stack (plain `fetch` against the KV v2 HTTP API, no client library, unchanged by this switch). `FieldDef.secret` (`rbac/src/data/providers.ts`) marks which per-provider fields actually need Vault — today OCI's `privateKey`/`passphrase`, Biznet's `xToken`, and AWS's `secretAccessKey`; GCP/Alibaba's fields are all non-secret identifiers and never touch Vault, and AWS's own `accessKeyId` is likewise non-secret (only `secretAccessKey` is Vault-backed). `connections.ts`'s create/update routes split incoming `config` accordingly (non-secret → Postgres as always, secret → Vault at `cirrus/connections/{id}`, path stored in `secret_ref`); delete cleans up the Vault entry too. `internal.ts`'s collector-facing config endpoint merges the Vault secret back into `config` transparently, so a collector never knows or cares whether a field came from Postgres or Vault. Verified live end-to-end for both OCI and Biznet: created real connections through BFF→RBAC→Vault with fake credentials, confirmed Vault held the secret fields while Postgres held only non-secret ones, and hit each collector directly to confirm correct `AUTH_FAILED`/`UPSTREAM_ERROR` classification.
- Deferred: Helm charts, Kubernetes. Local dev is Docker Compose only (`docker-compose.yml` at repo root).
- Running it: copy `.env.example` to `.env`, fill in the Entra ID values, then `docker compose up -d --build` — this now also builds/serves the frontend at `http://localhost:5173` (stop any `npm run dev` first, same port). No manual migrate/seed step needed: `rbac/docker-entrypoint.sh` runs `dist/db/migrate.js` then `dist/db/seed.js` automatically on every container start, before the server starts listening — both are idempotent (Drizzle's migrator no-ops on already-applied migrations; seed looks up the admin by case-insensitive email before inserting), so this is safe on every restart, not just the first run. Seeding creates exactly one bootstrap Admin via `SEED_ADMIN_EMAIL`, named "Administrator" by default or `SEED_ADMIN_NAME` if set — no sample connections; those are for the person testing to create themselves.
- The frontend is wired to this — see the Frontend section above. `backend/shared-types` mirrors `frontend/src/types.ts` and is the contract both sides are expected to stay in sync with. `User.connectionIds` (alongside the pre-existing `AuthenticatedUser.connectionIds`, both from `rbac/src/lib/userDto.ts`) lets the Users & Roles drawer (`frontend/src/components/users/UserDrawer.tsx`) show and pre-check which cloud connections a Viewer can see, sending `accountConnectionIds` on `POST`/`PATCH /api/users` — only when the form's role is `viewer`; omitted for `admin` so promoting/demoting never touches existing assignments.

## PRD.md

`PRD.md` is the single source of truth for this project — **Cirrus**, a Cloud VM Inventory Dashboard. Status: Approved. It is written in Bahasa Indonesia prose with English used for role names, table headers, and UI labels (this mixed convention is intentional — keep it when editing).

Key facts to know before making changes to the PRD or (later) implementing against it:

- **What it is**: an internal, read-only dashboard that aggregates VM inventory across the company's own accounts on 5 cloud providers (AWS, GCP, Alibaba Cloud, OCI, Biznet Gio Cloud) — not a multi-tenant SaaS. Avoid "customer" framing when describing cross-account auth; use "akun cloud yang didaftarkan" / "tim pemilik akun" instead.
- **Current MVP scope (§4)**: inventory list + filter/search + RBAC/SSO only. Cost/billing was deliberately cut from the MVP and moved to §10 Roadmap (with the per-provider cost-API research preserved there so it isn't lost) — don't reintroduce cost UI/flows into MVP sections (§2–§9).
- **Roles (§3)**: exactly 2 — `Admin` (manage users/roles, manage cloud account connections, view all data) and `Viewer` (view inventory for assigned accounts/projects only).
- **Auth**: Microsoft Entra ID (Microsoft 365) via OIDC, single-tenant. Identity key is `oid`+`tid` (never `email`, which is mutable).
- **Architecture (§7)**: microservices, Docker for dev / Kubernetes for prod. Frontend SPA → API Gateway/BFF → Auth Service + RBAC Service → Inventory Aggregator → 5 Provider Collectors (one per cloud, each exposing a uniform `GET /instances`). Redis caches fetch results (TTL 2–5 min, with a cache-stampede lock); PostgreSQL holds app metadata only (never live-pulled VM data).
- **Per-provider credential model (§7.3)** — deliberately different per provider, verified against current docs, don't default back to "just use an API key" for all of them:
  - Alibaba Cloud: cross-account role assumption (`AssumeRole`) — Cirrus holds one shared "hub" credential in Vault, not a secret per registered account.
  - GCP: Workload Identity Federation — no static secret stored at all.
  - AWS, OCI & Biznet Gio Cloud: static per-account credentials (IAM User Access Key / API Signing Key / `x-token`) in Vault KV v2 — AWS deliberately moved off cross-account `AssumeRole` to this per-account model (simpler per-account setup, no hub/trust-policy, at the cost of a long-lived key vs. AWS's own recommended short-lived role assumption).
- **Tech stack (§8)**: React+TypeScript+Vite frontend; Go (using `errgroup` for collector fan-out) for Provider Collectors; Node.js/TypeScript for BFF/Aggregator/RBAC; PostgreSQL + Redis; HashiCorp Vault (KV v2); Helm umbrella chart (one subchart per microservice) for Kubernetes deploy.
