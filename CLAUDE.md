## Frontend (`frontend/`)

- Tech stack matches PRD §8: React + TypeScript + Vite; `oxlint` for linting (`npm run lint`); `tsc -b && vite build` for the build.
- State: a single `useCirrusApp()` hook (`src/state/useCirrusApp.ts`) holds all app state/actions — no external state library (Redux/Zustand etc.). Keep new state co-located there rather than introducing a second state mechanism.
- Styling: CSS variables per theme + component classes in `src/index.css`, not inline style-string builders (that was the source mockup's approach, deliberately not carried over). Dynamic/data-driven colors (provider brand colors, status colors) stay as inline `style`.
- Theme default: light mode, set via the initial `useState<Theme>('light')` in `src/state/useCirrusApp.ts`. There's no persistence or OS-preference (`prefers-color-scheme`) detection — theme choice is in-memory only and resets to light on reload.
- Data: no more mock data file — `src/api/client.ts` holds typed fetch wrappers for every BFF route, and `src/state/useCirrusApp.ts` is fetch-driven (bootstraps the session via `GET /auth/me`, then loads `providers`/`vms`/`connections`/`users` from the backend; `providers` now carries `fieldDefs`/`checklist`/`failureMessage` per-provider, replacing the old static `FIELD_DEFS`/`CHECKLIST`/`FAILURE_MSG` maps from PRD §7.3). Always fetch relative paths (`/api/...`, `/auth/...`), never an absolute `localhost:8080` URL — both the Vite dev server (`vite.config.ts`'s `server.proxy`) and the built container's nginx (`nginx.conf`) proxy those same relative paths to the BFF, so the identical bundle works unmodified in either mode. The two run on the same host port (5173) by convention — never both at once.
- The Sidebar's old "Preview role" toggle and Inventory's old "Preview" (loading/empty/outage) toggle are gone by design, not an oversight — once role and fetch state are server-driven, a client-side override of either would just lie to the user. Don't re-add them; if a design-preview mode is needed again, it should be a clearly-labeled dev-only affordance (see the `import.meta.env.DEV`-gated "Dev login" button in `LoginScreen.tsx` for the pattern), not a first-class UI control.
- Provider icons are bundled locally under `src/assets/providers/` (not hotlinked). Note for future icon updates: brandfetch's CDN blocks hotlinking without browser-like `User-Agent`/`Referer` headers on `curl`.
- Docker: `frontend/Dockerfile` is a multi-stage build (`node:24-alpine` → `nginx:stable-alpine`) per PRD §7's "Docker for dev" — keep base images current stable/LTS when touched, don't quietly pin to whatever the scaffold generated. It's wired into the root `docker-compose.yml` as the `frontend` service (port `5173:80`, `depends_on: bff`).

## Backend (`backend/`)

- npm workspaces monorepo: `shared-types` (mirrors `frontend/src/types.ts` — keep these in sync, it's the frontend-facing contract), plus `bff`, `auth`, `rbac`, `aggregator` — all Fastify services in TypeScript, run via `tsx` in dev and compiled (`tsc -b`) in their Docker images.
- `collectors/` is a *separate* Go workspace (`go.work`, not part of the npm workspace): `internal-kit` (shared HTTP envelope, stub-generation, and RBAC-config-fetch helpers only — `rbacclient.go`'s `GetConnectionConfig` is used identically by every real collector, but carries zero provider-specific logic itself) plus one independent module per provider (`aws/`, `gcp/`, `alibaba/`, `oci/`, `biznet/`) — each its own binary/container so a failure or bad release in one never affects the others (PRD §7.1's isolation goal).
- Service ownership boundaries: `rbac` is the *sole* owner of PostgreSQL (users, cloud connections, audit log — schema in `rbac/src/db/schema.ts`, Drizzle ORM); `aggregator` is the *sole* owner of Redis (per-`(provider, connectionId)` cache with a `SET NX PX` stampede lock, `aggregator/src/cache/lock.ts`); `bff` is the only service meant to be called from outside the Docker network and proxies/aggregates the others.
- Auth is real, not stubbed: `auth/` performs actual Microsoft Entra ID OIDC (Authorization Code + PKCE via `@azure/msal-node`), single-tenant, identity keyed on `oid`+`tid` per PRD §3. It mints its own ES256 JWT (via `jose`) and exposes a JWKS endpoint (`/.well-known/jwks.json`) that `bff` verifies sessions against. Needs real Entra ID app registration values (`ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET`) in `.env` — everything else in the stack works without them.
- Temporary dev-login bypass: `auth/src/routes/devLogin.ts` (`GET /dev-login?email=...`) logs in as any already-invited RBAC user without a real Entra ID redirect, gated by `DEV_LOGIN_ENABLED` (default off — never enable outside local dev). It reuses the same `RBAC /internal/upsert-on-login` call the real callback makes, so it can't invite/bypass RBAC, only skip the Microsoft redirect. `LoginScreen.tsx` surfaces it as an `import.meta.env.DEV`-only button, so it never ships in a production build. Delete this once Entra ID is fully wired up.
- Provider Collectors each expose the uniform `GET /instances?connectionId=...` contract from PRD §7.1, resolving their own connection config via a new RBAC internal endpoint (`GET /internal/connections/:id`, `rbac/src/routes/internal.ts`) — the Aggregator never sees or forwards credential material. **AWS** (`collectors/aws/`) assumes the connection's role via Cirrus's own hub credential (`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` env vars, picked up by the AWS SDK's default credential chain — Vault later just populates the same env vars, no code change needed then), then calls EC2 across every enabled region. **Alibaba Cloud** (`collectors/alibaba/`) does the RAM-role equivalent (`ALIBABA_CLOUD_ACCESS_KEY_ID`/`_SECRET`) against ECS. **GCP** (`collectors/gcp/`) uses real Workload Identity Federation — no static secret at all — via a new Auth Service capability (`POST /internal/wif-token`, `auth/src/routes/wif.ts` + `signWifToken()` in `auth/src/jwt.ts`, sharing the same signing key/JWKS as session tokens) exchanged through `golang.org/x/oauth2/google/externalaccount` against Google's real STS/IAM Credentials APIs, then Compute Engine. **OCI** (`collectors/oci/`) uses an API Signing Key (`common.NewRawConfigurationProvider` from `oci-go-sdk/v65`, per-connection `tenancyOcid`/`userOcid`/`fingerprint`/`privateKey`/`region`/`passphrase`), recurses every accessible compartment (`identity.ListCompartments` with `AccessLevel: Accessible`) and fans out `core.ListInstances` + boot/block volume (`blockstorage`) + VNIC (`core.ListVnicAttachments`/`GetVnic`) lookups per compartment to build full instance records. **Biznet Gio** (`collectors/biznet/`) has no official SDK, so it's a plain REST client against `api.portal.biznetgio.com` with an `x-token` header, fanning out in parallel to both the NEO Lite and NEO Lite Pro product lines (`/neolites/accounts`, `/neolite-pros/accounts`) and tolerating one line failing as long as the other succeeds; because Biznet's real OpenAPI spec declares empty response schemas for every endpoint, field extraction is deliberately defensive (`extractField`'s candidate-key lookup) rather than a confident fixed struct. None of the 5 collectors has been tested against a real successful fetch (no real hub credentials, GCP resources, or OCI/Biznet accounts exist yet) — only that they compile against the real SDKs and fail gracefully (`AUTH_FAILED`/`UPSTREAM_ERROR`) when given fake credentials; AWS/GCP were observed reaching real IMDS/STS endpoints, and OCI/Biznet were observed reaching OCI's real Identity API (genuine 401) and Biznet's real Portal API (genuine 400) respectively. Collector/Aggregator timeouts were raised accordingly (5s stub-era budget → 20s AWS / 10s Alibaba / 15s GCP / 20s OCI / 15s Biznet per collector, 25s at the Aggregator, `aggregator/src/cache/lock.ts`). `POST /api/connections/:id/test` (in `rbac`) is still a simulated success/failure, not a real per-provider validation call.
- Vault is real, not deferred: a `vault` service (`hashicorp/vault`, dev mode — in-memory, auto-unsealed, data doesn't survive a restart) backs `rbac/src/lib/vault.ts`, the *only* Vault client in this stack (plain `fetch` against the KV v2 HTTP API, no client library). `FieldDef.secret` (`rbac/src/data/providers.ts`) marks which per-provider fields actually need Vault — today just OCI's `privateKey`/`passphrase` and Biznet's `xToken`; AWS/GCP/Alibaba's fields are all non-secret identifiers and never touch Vault. `connections.ts`'s create/update routes split incoming `config` accordingly (non-secret → Postgres as always, secret → Vault at `cirrus/connections/{id}`, path stored in `secret_ref`); delete cleans up the Vault entry too. `internal.ts`'s collector-facing config endpoint merges the Vault secret back into `config` transparently, so a collector never knows or cares whether a field came from Postgres or Vault. Verified live end-to-end for both OCI and Biznet: created real connections through BFF→RBAC→Vault with fake credentials, confirmed Vault held the secret fields while Postgres held only non-secret ones, and hit each collector directly to confirm correct `AUTH_FAILED`/`UPSTREAM_ERROR` classification.
- Deferred: Helm charts, Kubernetes. Local dev is Docker Compose only (`docker-compose.yml` at repo root).
- Running it: copy `.env.example` to `.env`, fill in the Entra ID values, then `docker compose up -d --build` — this now also builds/serves the frontend at `http://localhost:5173` (stop any `npm run dev` first, same port). First run also needs `docker compose exec rbac node dist/db/migrate.js` followed by `... node dist/db/seed.js` (seeds one bootstrap Admin via `SEED_ADMIN_EMAIL` plus one sample connection per provider).
- The frontend is wired to this — see the Frontend section above. `backend/shared-types` mirrors `frontend/src/types.ts` and is the contract both sides are expected to stay in sync with. `User.connectionIds` (alongside the pre-existing `AuthenticatedUser.connectionIds`, both from `rbac/src/lib/userDto.ts`) lets the Users & Roles drawer (`frontend/src/components/users/UserDrawer.tsx`) show and pre-check which cloud connections a Viewer can see, sending `accountConnectionIds` on `POST`/`PATCH /api/users` — only when the form's role is `viewer`; omitted for `admin` so promoting/demoting never touches existing assignments.

## PRD.md

`PRD.md` is the single source of truth for this project — **Cirrus**, a Cloud VM Inventory Dashboard. Status: Approved. It is written in Bahasa Indonesia prose with English used for role names, table headers, and UI labels (this mixed convention is intentional — keep it when editing).

Key facts to know before making changes to the PRD or (later) implementing against it:

- **What it is**: an internal, read-only dashboard that aggregates VM inventory across the company's own accounts on 5 cloud providers (AWS, GCP, Alibaba Cloud, OCI, Biznet Gio Cloud) — not a multi-tenant SaaS. Avoid "customer" framing when describing cross-account auth; use "akun cloud yang didaftarkan" / "tim pemilik akun" instead.
- **Current MVP scope (§4)**: inventory list + filter/search + RBAC/SSO only. Cost/billing was deliberately cut from the MVP and moved to §10 Roadmap (with the per-provider cost-API research preserved there so it isn't lost) — don't reintroduce cost UI/flows into MVP sections (§2–§9).
- **Roles (§3)**: exactly 2 — `Admin` (manage users/roles, manage cloud account connections, view all data) and `Viewer` (view inventory for assigned accounts/projects only).
- **Auth**: Microsoft Entra ID (Microsoft 365) via OIDC, single-tenant. Identity key is `oid`+`tid` (never `email`, which is mutable).
- **Architecture (§7)**: microservices, Docker for dev / Kubernetes for prod. Frontend SPA → API Gateway/BFF → Auth Service + RBAC Service → Inventory Aggregator → 5 Provider Collectors (one per cloud, each exposing a uniform `GET /instances`). Redis caches fetch results (TTL 2–5 min, with a cache-stampede lock); PostgreSQL holds app metadata only (never live-pulled VM data).
- **Per-provider credential model (§7.3)** — deliberately different per provider, verified against current docs, don't default back to "just use an API key" for all of them:
  - AWS & Alibaba Cloud: cross-account role assumption (`AssumeRole`) — Cirrus holds one shared "hub" credential per provider in Vault, not a secret per registered account.
  - GCP: Workload Identity Federation — no static secret stored at all.
  - OCI & Biznet Gio Cloud: static per-account credentials (API Signing Key / `x-token`) in Vault KV v2 — confirmed this is still the correct pattern for these two.
- **Tech stack (§8)**: React+TypeScript+Vite frontend; Go (using `errgroup` for collector fan-out) for Provider Collectors; Node.js/TypeScript for BFF/Aggregator/RBAC; PostgreSQL + Redis; HashiCorp Vault (KV v2); Helm umbrella chart (one subchart per microservice) for Kubernetes deploy.
