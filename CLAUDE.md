## Frontend (`frontend/`)

- Tech stack matches PRD §8: React + TypeScript + Vite; `oxlint` for linting (`npm run lint`); `tsc -b && vite build` for the build.
- State: a single `useCirrusApp()` hook (`src/state/useCirrusApp.ts`) holds all app state/actions — no external state library (Redux/Zustand etc.). Keep new state co-located there rather than introducing a second state mechanism.
- Styling: CSS variables per theme + component classes in `src/index.css`, not inline style-string builders (that was the source mockup's approach, deliberately not carried over). Dynamic/data-driven colors (provider brand colors, status colors) stay as inline `style`.
- Theme default: light mode. `src/state/useCirrusApp.ts`'s `theme` state initializes from `localStorage` (`getInitialTheme()`, key `cirrus-theme`, falling back to `'light'` if unset/invalid) and a `useEffect` persists every `setTheme` call back to that same key — added after a real bug where both login paths (`window.location.href` to `/auth/login` or `/auth/dev-login`, see Backend section) do a full browser navigation, so the Auth Service's post-login `reply.redirect()` back to the SPA root remounted React and silently reset an in-memory-only theme choice to light. Still no OS-preference (`prefers-color-scheme`) detection.
- Data: no more mock data file — `src/api/client.ts` holds typed fetch wrappers for every BFF route, and `src/state/useCirrusApp.ts` is fetch-driven (bootstraps the session via `GET /auth/me`, then loads `providers`/`vms`/`connections`/`users` from the backend; `providers` now carries `fieldDefs`/`setupGuide`/`failureMessage` per-provider, replacing the old static `FIELD_DEFS`/`CHECKLIST`/`FAILURE_MSG` maps from PRD §7.3 — the wizard step-2 side card renders `setupGuide` under the heading "How to get these values", provider-specific instructions for obtaining the credential values from each provider's own console, not a list of API calls Cirrus makes to verify them; GCP's card additionally renders a "Download cirrus-jwks.json" button, `wizardProviderMeta?.id === 'gcp'`-gated, that's just a plain `<a href="/api/gcp/jwks" download>` — same-origin so the session cookie rides along automatically, no `api/client.ts` fetch wrapper needed — since GCP's Workload Identity Federation needs that file uploaded manually, see Backend section). Always fetch relative paths (`/api/...`, `/auth/...`), never an absolute `localhost:8080` URL — both the Vite dev server (`vite.config.ts`'s `server.proxy`) and the built container's nginx (`nginx.conf`) proxy those same relative paths to the BFF, so the identical bundle works unmodified in either mode. The two run on the same host port (5173) by convention — never both at once.
- Routing is real, not a `screen`-state switch: `src/router.tsx` defines a code-based TanStack Router (`@tanstack/react-router`) route tree — `/` (login, redirects to `/inventory` if already authenticated), and a protected layout route (redirects to `/` if not authenticated) with children `/inventory`, `/connections`, `/connections/new` (the add-connection wizard), `/users` (the latter three additionally guarded admin-only via `beforeLoad`, mirroring `Sidebar.tsx`'s nav-item visibility but enforced even on a direct URL visit). `App.tsx` still calls `useCirrusApp()` once and only mounts `<RouterProvider router={router} context={{ app }} />` after `authChecked` — this defers every route guard until the async session check resolves, avoiding a race, and is the documented TanStack pattern for injecting hook-derived context into a router created once at module scope. `useCirrusApp.ts` no longer holds a `screen` state at all; navigation goes through `router.navigate(...)` (confirmed via Context7 to work imperatively from a plain hook, not just inside components) or `<Link>` (used in `Sidebar.tsx`, with `activeProps` driving the nav-item highlight that `screen === X` checks used to do). `AppShell.tsx` is now just `ProtectedLayout` (Sidebar + an `<Outlet/>`) plus a small `ScreenLayout` helper each route's page component wraps itself in — a single `<Outlet/>` can only render one matched component, so header+body per screen can no longer be split across two containers the way the old `screen`-switch did.
- **`context={{ app }}` on `RouterProvider` is for `beforeLoad` guards only, never for rendering** — this was a real bug, not a hypothetical: route page components originally read the live `app` via `xxxRoute.useRouteContext()`, but TanStack Router only recomputes route context on a fresh match (navigation or `router.invalidate()`), so it doesn't reactively pick up state changes from clicks between navigations — confirmed via Context7 against TanStack's own docs/GitHub issues. Symptom was silent: clicking "Invite User" or a Connection card did nothing, yet the state change *had* happened — navigating away and back would reveal a drawer that was already open. Fixed by adding `src/state/AppContext.tsx` (a plain `createContext`/`useApp()` pair), providing it in `App.tsx` via `<AppContext.Provider value={app}>` wrapping `<RouterProvider>`, and switching every route page component plus `ProtectedLayout` from `useRouteContext()` to `useApp()` for rendering. `beforeLoad`/`requireAdmin` still correctly read `context.app` — that per-navigation guard use was never broken. If a new route page component is added, give it `useApp()`, not `useRouteContext()`.
- The Sidebar's old "Preview role" toggle, Inventory's old "Preview" (loading/empty/outage) toggle, and Connections' old "Preview: Default/Empty" toggle are all gone by design, not an oversight — once role and fetch state are server-driven, a client-side override of any of them would just lie to the user. Don't re-add them; if a design-preview mode is needed again, it should be a clearly-labeled dev-only affordance (see the `import.meta.env.DEV`-gated "Dev login" button in `LoginScreen.tsx` for the pattern), not a first-class UI control.
- Inventory's "Providers connected" stat card (`InventoryScreen.tsx`'s `stats` useMemo) counts `connections.filter(c => c.status === 'active').length`, not `providers.length` — `providers` is the static 5-entry provider-*type* catalog from `GET /api/providers` (used for the Add-connection wizard's field defs), never the live `cloud_connections` state, so counting it would always show 5 regardless of how many connections actually exist.
- Provider icons are bundled locally under `src/assets/providers/` (not hotlinked). Note for future icon updates: brandfetch's CDN blocks hotlinking without browser-like `User-Agent`/`Referer` headers on `curl`.
- `Toast` (`src/components/shared/Toast.tsx`) is self-animating, not parent-mounted/unmounted: it owns its own `phase` (`'entering' | 'exiting' | null`) state, so when `app.toast` clears it animates out (slide+fade, `toastOut` keyframe) for 200ms before actually unmounting, instead of vanishing instantly. Positioned bottom-right with equal margins (`bottom: 10px; right: 10px` in `index.css`, slide direction flipped to match) — it used to be bottom-center with no animation, then briefly top-right (`top: 88px`, offset below the 72px per-screen header row) to avoid overlapping header action buttons (Invite User, Add Connection, etc.), before settling on bottom-right; `10px` (not the more typical `24px`) so it clears the last row of a full-height Inventory table instead of overlapping it.
- Docker: `frontend/Dockerfile` is a multi-stage build (`node:24-alpine` → `nginx:stable-alpine`) per PRD §7's "Docker for dev" — keep base images current stable/LTS when touched, don't quietly pin to whatever the scaffold generated. It's wired into the root `docker-compose.yml` as the `frontend` service (port `5173:80`, `depends_on: bff`). Its healthcheck probes `http://127.0.0.1/`, not `http://localhost/` — `nginx` binds `0.0.0.0:80` only (IPv4), but `localhost` resolves to `::1` first inside the container, so `wget` hit "connection refused" on every single probe despite the site itself working fine, permanently marking the container `unhealthy`. This isn't just cosmetic: Traefik (the external reverse proxy fronting `cirrus.example.com`, config outside this repo) excludes `unhealthy` containers from routing entirely, so this alone took the public dashboard down with a bare Traefik-level 404 (no matching router) even though every backend service was otherwise fine.
- Inventory's initial load and Refresh button no longer wait for every provider before showing anything: `GET /api/vms`/`POST /api/vms/refresh` are NDJSON streams (one JSON frame per line — `start`/`connection`/`done`, `VmStreamFrame` in `shared-types`/`types.ts`), not a single combined response — see Backend section below for the server side. `useCirrusApp.ts` holds `vmsByConnection`/`vmErrorsByConnection` (`Map<connectionId, ...>`) instead of flat `vms`/`vmErrors` arrays; `vms`/`vmErrors` are now derived (`useMemo`) by flattening those maps, so nothing downstream (`InventoryScreen.tsx`, filters, stats) needed an interface change. `consumeVmStream` (shared by the bootstrap effect and `refreshInventory`) updates one connection's slice of the maps per `connection` frame as it arrives and tracks a `vmProgress: {done, total} | null` used to render a "Refreshing X/Y connections…" indicator next to the Refresh button (`InventoryHeader` in `InventoryScreen.tsx`) — deliberately "connections" not "providers" in the copy, since a provider can have more than one registered connection (e.g. AWS with 2). The `start` frame carries the full current `connectionIds` list (not just a count), which `consumeVmStream` also uses to prune any connection deleted since the last load out of both maps immediately, so a removed connection's VMs don't linger. `InventoryScreen.tsx`'s full-table skeleton (`showSkeleton`) now only shows when `vms.length === 0` — once the first connection frame lands the table renders and later frames update rows in place, no more blank-whole-table-until-everything-finishes. The bootstrap effect's stream is cancellable (`AbortController`, `getVmsStream`'s optional `signal` param) so React StrictMode's dev-mode double-effect-invocation aborts the stale run instead of leaving two overlapping streams racing on the same state; `refreshInventory` doesn't need this since it's click-triggered (can't be StrictMode-doubled) and already guards re-entrant clicks via `vmProgress`.
- **iOS Safari safe-area fix, remaining P0.5 gap, closed.** The fix from `d4ca68f` had only ever been applied inline to Sidebar's own off-canvas drawer — `UserDrawer.tsx`/`EditConnectionDrawer.tsx`/`VmDetailDrawer.tsx` all share `.drawer-panel` in `index.css`, which never got the same treatment, so their bottom action rows could sit under the home-indicator bar on notched iPhones. Fixed once at the shared class level (`env(safe-area-inset-bottom)` added to `.drawer-panel`'s bottom padding, base rule and its `@media (max-width: 640px)` override) instead of duplicating Sidebar's per-component inline-style fix three more times.
- **Connections/Users loading state, remaining P0.5 gap, closed.** `loadConnections`/`loadUsers` were a bare `.then(setX)`/`.catch(...)`, so a slow first load could flash straight to the empty/error copy. `useCirrusApp.ts` now tracks `connectionsLoading`/`usersLoading` (default `true`, cleared in a `.finally()` on each loader, mirroring `isLoadingVms`), and `ConnectionsScreen.tsx`/`UsersScreen.tsx` each gained a `showLoading` branch (checked before `showError`/`showEmpty`, same ordering `showSkeleton` uses in Inventory) rendering new `ConnectionCardSkeleton.tsx`/`UserRowSkeleton.tsx` — dedicated chip-placeholder components (own markup, not `SkeletonRows.tsx` reused) since the card-grid and 3-column-table shapes don't match Inventory's 10-column table. `UserRowSkeleton` wraps a full real `<table>` (not just skeleton `<tr>`s inside an existing `<tbody>`) in its `<phantom-ui>` — nesting `<phantom-ui>` directly as a `<tbody>` child would trip the CSS table anonymous-box-generation rules, since it isn't itself a `tr`/`col`/etc.
- **Connections screen crash, fixed.** Discovered live in production (via Playwright, while verifying the P1 security-headers change) — `ConnectionsScreen.tsx` crashed with `TypeError: Cannot read properties of undefined (reading 'name')` on every real connection at once. Root cause was a load-order race, not a provider-id mismatch: the bootstrap effect in `useCirrusApp.ts` fires `getProviders(true)` and `loadConnections()` as two independent, unawaited fetches, and there was a `connectionsLoading` state but no `providersLoading` one — so if `GET /api/connections` resolved before the (heavier) `GET /api/providers?includeFieldDefs=true` call, `ConnectionsScreen.tsx`'s `showLoading` (gated only on `connectionsLoading`) flipped `false` while `app.providers` was still `[]`, and every row's `providerMap[c.provider]` lookup came back `undefined` simultaneously. `useCirrusApp.ts` now has a real `providersLoading` state (same `.finally()` convention as `connectionsLoading`/`usersLoading`), and `ConnectionsScreen.tsx`'s `showLoading` is `app.providersLoading || (app.connectionsLoading && connectionsRows.length === 0)` — deliberately not gated behind `connectionsRows.length === 0` alone, since that's exactly the condition that let a non-empty connections list race ahead of an empty provider map. Separately, as defense-in-depth against a genuine (not just racy) `GET /api/providers` failure — there's no `providersError`/retry state for it today, just a toast, so `providers` can stay `[]` forever — `ProviderBadge.tsx`'s `provider` prop and `ConnectionCard.tsx`'s `providerMeta` prop are now `| undefined` with a neutral fallback (muted badge, "Unknown provider" label) instead of an unguarded `.name`/`.bg` read; `EditConnectionDrawer.tsx` had the identical unguarded pattern (a `!` compile-time-only assertion immediately followed by an unguarded `.name`, despite already correctly using `?.fieldDefs ?? []` two lines earlier in the same function) and got the same fix.

## Backend (`backend/`)

- npm workspaces monorepo: `shared-types` (mirrors `frontend/src/types.ts` — keep these in sync, it's the frontend-facing contract), plus `bff`, `auth`, `rbac`, `aggregator` — all Fastify services in TypeScript, run via `tsx` in dev and compiled (`tsc -b`) in their Docker images.
- `collectors/` is a *separate* Go workspace (`go.work`, not part of the npm workspace): `internal-kit` (shared HTTP envelope and RBAC-config-fetch helpers only — `rbacclient.go`'s `GetConnectionConfig` is used identically by every real collector, but carries zero provider-specific logic itself; the old deterministic fake-fleet generator (`stub.go`) from before every collector made real API calls has been deleted — no dead stub-generation code left) plus one independent module per provider (`aws/`, `gcp/`, `alibaba/`, `oci/`, `biznet/`) — each its own binary/container so a failure or bad release in one never affects the others (PRD §7.1's isolation goal).
- Service ownership boundaries: `rbac` is the *sole* owner of PostgreSQL (users, cloud connections, audit log — schema in `rbac/src/db/schema.ts`, Drizzle ORM); `aggregator` is the *sole* owner of Redis (per-`(provider, connectionId)` cache with a `SET NX PX` stampede lock, `aggregator/src/cache/lock.ts`); `bff` is the only service meant to be called from outside the Docker network and proxies/aggregates the others.
- Auth is real, not stubbed: `auth/` performs actual Microsoft Entra ID OIDC (Authorization Code + PKCE via `@azure/msal-node`), single-tenant, identity keyed on `oid`+`tid` per PRD §3. It mints its own ES256 JWT (via `jose`) and exposes a JWKS endpoint (`/.well-known/jwks.json`) that `bff` verifies sessions against. Needs real Entra ID app registration values (`ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET`) in `.env` — everything else in the stack works without them.
- `auth/src/oidc/callback.ts`'s `/callback` route is hit via a top-level browser redirect from Microsoft (not a fetch/XHR), so it never returns raw JSON on failure — every error branch (`INVALID_FLOW`/`STATE_MISMATCH`/`OAUTH_ERROR`/`NETWORK_ERROR`/`MISSING_CLAIMS`/`NOT_INVITED`/`RBAC_UNAVAILABLE`) redirects back to `POST_LOGIN_REDIRECT` with `?authError=<code>` via the shared `redirectWithError` helper (`auth/src/oidc/errorRedirect.ts`, also used by `devLogin.ts`); the frontend's login route (`frontend/src/router.tsx`'s `loginRoute`) reads that param via `validateSearch`, maps the code to a human message, shows it as a red-variant `Toast` (`Toast`/`showToast` now take an optional `'success' | 'error'` variant, default `'success'`, in `frontend/src/state/useCirrusApp.ts`/`frontend/src/components/shared/Toast.tsx`), then strips the query param via a `replace: true` navigation. This replaced an incident where a real transient network blip on the outbound token-exchange call to `login.microsoftonline.com` (msal-node `AuthError` with `errorCode: 'network_error'`) surfaced as literal JSON text in the browser. `acquireTokenByCode` is now wrapped in `acquireTokenWithRetry` (one retry, 500ms apart, only for that specific `network_error` code) to self-heal the common transient case silently. Separately, the `auth_flow` cookie (PKCE verifier + state, `signed`, `maxAge: 600`) used to be cleared *before* attempting the token exchange, so a failed exchange followed by a hard-refresh of the same callback URL always died with `INVALID_FLOW` even though the code might still have been exchangeable — it's now only cleared on terminal outcomes (state mismatch, Microsoft's own `error` param, or *after* a successful exchange), never on a retryable network failure, so a manual hard-refresh within the cookie's 10-minute window can still retry.
- Temporary dev-login bypass: `auth/src/routes/devLogin.ts` (`GET /dev-login?email=...`) logs in as any already-invited RBAC user without a real Entra ID redirect, gated by `DEV_LOGIN_ENABLED` (default off — never enable outside local dev). It reuses the same `RBAC /internal/upsert-on-login` call the real callback makes, so it can't invite/bypass RBAC, only skip the Microsoft redirect. `LoginScreen.tsx` surfaces it as an `import.meta.env.DEV`-only button, so it never ships in a production build. Delete this once Entra ID is fully wired up. `env.ts`'s `devLoginEnabled` now also requires `NODE_ENV !== 'production'` as a second, independent gate (a `devLoginSuppressedByNodeEnv` flag logs a distinct warning in `server.ts` when the two disagree) — added as a production-readiness hardening pass so a stray `DEV_LOGIN_ENABLED=true` left in a production `.env` can't reactivate the bypass once deployed with `docker-compose.prod.yml` (which sets `NODE_ENV=production`; see "Running it" below).
- Provider Collectors each expose the uniform `GET /instances?connectionId=...` contract from PRD §7.1, resolving their own connection config via a new RBAC internal endpoint (`GET /internal/connections/:id`, `rbac/src/routes/internal.ts`) — the Aggregator never sees or forwards credential material. **AWS** (`collectors/aws/`) uses a per-connection static IAM user Access Key (`accessKeyId`/`secretAccessKey`, no hub account or role assumption — `buildAWSConfig` in `internal/instances.go` builds an `aws.Config` directly from the connection's own credentials via `credentials.NewStaticCredentialsProvider`, fresh per request, mirroring OCI's `buildConfigProvider` pattern), then calls EC2 across every enabled region — **EC2 only, not Lightsail**: `AmazonEC2ReadOnlyAccess` (the policy suggested in the setup guide) doesn't grant any `lightsail:*` actions either, so a company VM running on Lightsail rather than EC2 simply won't appear in inventory today (PRD §11 item 6). **AWS is now confirmed against a real successful fetch** — 2 real per-connection IAM users returned real EC2 instances (including in `ap-southeast-3`/Jakarta), but the first attempt surfaced two bugs, both now fixed in `internal/instances.go`: (1) the collector's old flat 20s deadline for the *entire* multi-region fan-out (`DescribeRegions` then `DescribeInstances`+`DescribeVolumes` per region via `errgroup`) was consistently too short for a real account's full region sweep, and since `collectorkit.WithTimeout` is a thin wrapper over Go's `http.TimeoutHandler` — which does **not** cancel the underlying request context on timeout — every timed-out request kept running to completion in the background anyway, wasting AWS API calls on every retry; each region's `DescribeInstances`+`DescribeVolumes` pair is now bounded by its own `context.WithTimeout(gctx, 20*time.Second)` sub-deadline (skipped gracefully, logged, and excluded rather than failing the whole fetch) so one slow/unreachable region can no longer starve every other region of the shared budget, `handleInstances` now derives its own cancellable `context.WithTimeout(r.Context(), 45*time.Second)` instead of relying solely on `WithTimeout`'s non-cancelling wrapper, and the outer per-request budget was raised 20s → 45s to fit a real region sweep now that no single region can blow it. (2) A region whose `DescribeInstances` succeeded but whose subsequent `DescribeVolumes` call timed out used to have its instances silently discarded entirely (this is exactly what happened to the real `ap-southeast-3` instances on the first real fetch) — it now keeps those instances with empty disk info instead of dropping the whole region. **Alibaba Cloud** (`collectors/alibaba/`) originally did the RAM-role equivalent of AWS's model (`AssumeRole` via a shared hub AccessKey/Secret in the collector's own env), then a per-connection static RAM User AccessKey/Secret scoped to one Region ID picked by the Admin, and has since been switched to fan out across every region like AWS too — `FetchInstances` in `internal/instances.go` calls `ecs:DescribeRegions` once (via a `defaultBootstrapRegion` client, mirroring AWS's own bootstrap-region pattern) to discover every region the connection's static AccessKey (`buildAlibabaCredential`, mirroring `buildAWSConfig`, built fresh per request, no hub identity, no role assumption) can reach, then fans out `DescribeInstances` per region via `errgroup`. The `regionId` wizard field is gone — Cirrus auto-discovers regions instead of an Admin picking one upfront. One real difference from AWS's fan-out: Alibaba's tea-generated SDK methods don't accept a Go context at all, so a `context.WithTimeout` around a call can't actually cancel it — each region is instead bounded by the SDK's own `ReadTimeout`/`ConnectTimeout` config fields (`regionFetchTimeoutMs` = 15s, set per-region client in `newECSClient`), and a timed-out region is detected via `errors.As(err, &netErr) && netErr.Timeout()` and skipped gracefully rather than failing the whole fetch — the outer `/instances` handler budget was raised 10s → 30s accordingly (kept below AWS's 45s since Alibaba only makes one paginated `DescribeInstances` call per region, no extra `DescribeVolumes`/`DescribeInstanceTypes` round-trips). **GCP** (`collectors/gcp/`) uses real Workload Identity Federation — no static secret at all — via a new Auth Service capability (`POST /internal/wif-token`, `auth/src/routes/wif.ts` + `signWifToken()` in `auth/src/jwt.ts`, sharing the same signing key/JWKS as session tokens) exchanged through `golang.org/x/oauth2/google/externalaccount` against Google's real STS/IAM Credentials APIs, then Compute Engine. Since Google's WIF OIDC provider still needs the Auth Service's JWKS somehow and only `frontend` sits behind Traefik (`auth` has no public route and no `/.well-known/openid-configuration` discovery endpoint), GCP's setup guide has whoever's registering a connection upload the JWKS to Google manually rather than relying on live discovery — `GET /api/gcp/jwks` (`bff/src/routes/gcp.ts`, Admin-gated via `requireAdmin`, same pattern as `connections.ts`/`users.ts`) fetches `auth`'s `/.well-known/jwks.json` internally via `env.authUrl` and re-serves it as a `Content-Disposition: attachment` download, so an Admin can get the file from the wizard itself instead of `curl`-ing the Auth Service's host-published port by hand. **OCI** (`collectors/oci/`) uses an API Signing Key (`common.NewRawConfigurationProvider` from `oci-go-sdk/v65`, per-connection `tenancyOcid`/`userOcid`/`fingerprint`/`privateKey`/`region`/`passphrase`), recurses every accessible compartment (`identity.ListCompartments` with `AccessLevel: Accessible`) and fans out `core.ListInstances` + boot/block volume (`blockstorage`) + VNIC (`core.ListVnicAttachments`/`GetVnic`) lookups per compartment to build full instance records. **OCI is now confirmed against a real successful fetch** — a real tenancy with a real compute-read-only-scoped connection returned zero VMs on every Refresh despite a passing `/test`, tracked down (via a direct `curl` against the collector's own `/instances?connectionId=...`, bypassing the UI) to a hard crash rather than a policy/region problem: `listAllBootVolumeAttachments`/`listAllVolumeAttachments` in `internal/instances.go` built their requests with only `CompartmentId` set, but OCI's `ListBootVolumeAttachments` API (confirmed against the SDK's own generated struct, `oci-go-sdk/v65/core.ListBootVolumeAttachmentsRequest`) marks `AvailabilityDomain` `mandatory:"true"` — so the SDK's own request marshaler rejected the call locally, On first boot the entrypoint runs `vault operator init` (5 Shamir key shares / 3 threshold) and persists the unseal keys + initial root token into `/vault/init/.cirrus-init/init.txt`, backed by a dedicated `vault-init` Docker volume — **deliberately separate from `vault-file`**, after a production-readiness review flagged that the original design (this file lived at `/vault/file/.cirrus-init/init.txt`, inside the same volume as Vault's own encrypted data) defeated Shamir separation-of-duty in practice: anyone with access to that one volume got both the lock and the key. That `vault-init` volume split introduced a real first-boot bug of its own, hit on this environment's first production bring-up: unlike `vault-file`, whose path is baked into the `hashicorp/vault` image (already owned by `vault:vault`, so Docker copies that ownership into a freshly created named volume), `vault-init` is a path the image has never heard of — a brand-new named volume mounted there comes up owned by `root:root`. `entrypoint.sh` runs entirely as the image's non-root `vault` user (uid 100/gid 1000 — see the `disable_mlock` note above for why there's no root step at all), so it can't `mkdir`/write into a root-owned mountpoint; the stock image's own `docker-entrypoint.sh` would normally `chown` a path like this, but only when invoked as `vault ...`, and our command is `sh /vault/entrypoint.sh`, so that logic never fires. Worse, `entrypoint.sh` has no `set -e`, so the failed `mkdir` didn't stop the script — `vault operator init` still ran and generated a real Shamir key set, which then failed to write to disk, sealing the backing store with unseal keys that were never persisted anywhere (unrecoverable; required wiping `vault-file`+`vault-init` and re-initializing from scratch). Two follow-up gaps surfaced discussing the above: every log line only carried `pid`/`hostname` (the container ID) with nothing human-readable identifying which of the 4 services emitted it, and the shared `setErrorHandler` (identical across all 4) logged 5xx errors via `app.log.error({ err }, ...)` — the *root* logger — instead of the request-scoped child logger Fastify already attaches to every request (confirmed via Context7 that Fastify's default `genReqId` is a per-process `req-${counter.toString(36)}` counter, explaining the short `req-7`/`req-a`-style IDs already seen in this session's logs), so an error line could never be matched back to the `incoming request`/`request completed` lines for that same request — the second handler param was even named `_req` for "intentionally unused". Both fixed: each `Fastify({...})` call now also sets `logger.name` (`'bff'`/`'auth'`/`'rbac'`/`'aggregator'`), and `setErrorHandler`'s `_req` param is now `req`, logging via `req.log.error(...)` instead of `app.log.error(...)` — verified live by temporarily throwing from a scratch route and confirming the resulting `unhandled request error` line shared the exact same `reqId` as that request's `incoming request`/`request completed` lines. (Cross-service request tracing — propagating one request ID across the bff→auth/rbac→collector hop chain — was discussed but deliberately deferred, not part of this fix.)
- **Cross-service request tracing, the deferred item above, now built.** `frontend/nginx.conf` mints one ID per incoming request via nginx's built-in `$request_id` (random, no config needed) and forwards it as `X-Request-Id` on all 3 proxied locations (`/api/vms`/`/api/`/`/auth/`) — critically via `proxy_set_header`, which unconditionally *overwrites* whatever a browser sent, so no service ever trusts a client-supplied trace ID. `bff`/`rbac`/`aggregator` each gained `requestIdHeader: 'x-request-id'` on their `Fastify({...})` call (adopts that header as `request.id`/`reqId` instead of generating an unrelated one) plus a small per-service `lib/requestContext.ts` (`AsyncLocalStorage<string>`, Node core, no new dependency — a new pattern for this codebase, chosen deliberately over threading a `reqId` param through every function signature, since `bff`'s `rbacClient.ts`/`aggregatorClient.ts` alone would've needed it across 12+ exported functions and their route-file call sites) populated once per request via an `onRequest` hook (`requestIdStorage.enterWith(req.id)`), then read back inside each service's outbound-call helpers (`bff`'s `clients/rbacClient.ts`/`clients/aggregatorClient.ts`, `rbac`'s `lib/collectorClient.ts`/`lib/vault.ts`, `aggregator`'s `cache/lock.ts`) to attach `x-request-id` alongside the existing `x-internal-secret` header. `auth` also gained `requestIdHeader` (so it adopts the id bff's `@fastify/http-proxy` already forwards through unmodified for `/auth/*`) but deliberately **not** the `AsyncLocalStorage` plumbing — its only 2 outbound calls to `rbac` (`devLogin.ts`, `oidc/callback.ts`) are inline within route handlers that already have `req` in scope, so they just use `req.id` directly; adding the storage machinery there would've been dead weight. Go collectors got the narrower end of this: a new `internal-kit/requestid.go` (`WithRequestID`/`context.WithValue`, Go's own idiomatic equivalent) reads the incoming `X-Request-Id` header in each collector's `handleInstances`/`handleTest` and `rbacclient.go`'s `GetConnectionConfig` forwards it on their one outbound call back to `rbac` — closing that leg of the chain without adding new per-request logging to collectors themselves (they have none today; that's `TODO.md`'s separate P2 observability item, not part of tracing propagation). One deliberate non-goal: a single logical OIDC login (`/auth/login` → redirect to Microsoft → `/auth/callback`) still gets two different trace IDs, since nginx mints a fresh one per top-level HTTP request and those two legs are genuinely separated by an external hop to Microsoft — not a gap, a real boundary. Verified live: one request's `X-Request-Id` traced identically through `bff`→`rbac` logs; a manually spoofed client-supplied header confirmed overwritten by nginx's own generated value before reaching `bff`; `go build ./...` (via each collector's Docker build, since this environment has no local `go` toolchain) confirmed the Go side compiles.
- **Internal TLS — decided: accept the risk, documented, not built** (P1 security hardening item 5 in `TODO.md`). `docker-compose.yml`'s `networks:` section shows the real topology: only `frontend` joins the external `proxy` network Traefik lives on; every other service — `bff`/`auth`/`rbac`/`aggregator`/all 5 collectors/`postgres`/`redis`/`vault` — has no explicit `networks:` key, so they all implicitly share one flat Compose `default` bridge network on a single Docker host. Given that shape, the realistic attack path internal TLS protects against is a network sniffer positioned *between* two containers on that same bridge — reaching that position already requires root on the host or code execution inside another container with raw-socket access, at which point a sniffer could equally well read `INTERNAL_SHARED_SECRET` off the wire (sent as a plain header today) and impersonate a service anyway, so TLS's marginal benefit here is real but narrower than it first sounds. Cirrus also handles cloud credentials (Vault-encrypted at rest) and VM inventory metadata for an internal company tool, not data under a compliance regime that mandates encryption-in-transit internally. A specific alternative was raised and ruled out before landing on this decision: reusing Traefik's existing Let's Encrypt cert for Vault's listener (`tls_disable = 1` in `vault/config.hcl`) doesn't work — that cert is issued via ACME for the public domain (`cirrus.example.com`/`*.example.com`) and can't include the internal Docker hostname (`vault`) in its SAN list, so standard TLS hostname verification would fail even if the cert file were reachable, which it isn't anyway (Traefik's config and cert storage are external to this repo). The real alternative — a self-signed internal CA issuing a cert for the `vault` hostname specifically, HashiCorp's own recommended pattern for Vault — is genuine, ongoing PKI work (manual issuance/rotation, no Let's-Encrypt-style auto-renewal) judged disproportionate for this single-host deployment once that cost was made concrete. This is an explicit, not permanent, acceptance — revisit if the deployment ever goes multi-host or a compliance requirement appears.
- **Backup procedure for Postgres + Vault, now built** (P1 security hardening item 6 in `TODO.md`) — previously no backup/restore mechanism existed for either. Two new sidecar services, `postgres-backup`/`vault-backup` (`docker-compose.yml`), each a stock base image running a bind-mounted hand-rolled sleep-loop script (`backup/postgres-entrypoint.sh`/`backup/vault-entrypoint.sh` — same "no cron-expression library" convention as `rbac/src/scheduler.ts`): dump/archive → prune backups past `*_RETENTION_DAYS` → sleep `*_INTERVAL_SECONDS` → repeat, defaults daily/1 week. Output goes to a **host bind-mounted** `./backups/postgres`/`./backups/vault` (gitignored), not a Docker-managed volume, so it's trivially copyable off the host (rsync/cloud-sync — that off-box shipping step itself stays a manual/external operational task, same precedent as the P0 Vault fix leaving root-token rotation manual). `postgres-backup` is the same `postgres:17-alpine` image as the real `postgres` service (keeps `pg_dump`'s version matched to the server) and connects over the network (`pg_dump -h postgres`) rather than touching the `pgdata` volume directly, so a corrupted/lost `pgdata` can't take the backups down with it. `vault-backup` is `alpine:3.22` tarring a **read-only** mount of `vault-file` — the only backup method the file storage backend actually supports (no hot-backup API, unlike the Raft backend's `vault operator raft snapshot`, which doesn't apply since this deployment uses `storage "file"`); a real, stated caveat is that this is a filesystem-level snapshot of a live Vault, not an atomic backend-native export, so a backup could in theory land mid-write — accepted for this deployment's low-write-throughput pattern (connections created/edited rarely). **`vault-init` (the unseal keys/root token) is deliberately never backed up by either script** — that volume's content is meant to be extracted once into a password manager per the existing bootstrap docs, and auto-copying root credentials to another on-host location would widen exposure, not reduce it; this also directly satisfies the TODO item's "decoupled from wherever the unseal keys end up" requirement, since Vault's actual backup never shares a location with them. Both scripts capture their dump/tar command's exit status explicitly (not via shell pipefail, since Alpine's `/bin/sh` is `busybox ash`) before atomically renaming a `.tmp` file into place, and `chmod 600` every written file. Verified live end-to-end: both wrote a valid file on first boot (`gzip -t`/`tar -tzf` both clean); the Postgres dump was fully restored into a throwaway `postgres:17-alpine` container and confirmed real row counts back (`users`/`cloud_connections`/`audit_log`); the Vault tar was extracted into a scratch directory and confirmed to contain exactly Vault's file-backend layout (`core/`/`logical/`/`sys/`) with no `.cirrus-init`/unseal-key material present; retention pruning confirmed by seeding a manually-aged dummy file and observing it (and only it) get deleted on the next cycle.
- **Log size caps, now built** (P1 security hardening item 7 in `TODO.md`) — every one of the 16 services in `docker-compose.yml` used the default `json-file` driver with no rotation, so container logs could grow unbounded on the host disk. A single `x-logging: &default-logging` YAML anchor (`driver: json-file`, `max-size: "10m"`, `max-file: "3"` — 30MB cap per service) is referenced via `logging: *default-logging` on every service, rather than duplicating that identical 4-line block 16 times — a deliberate departure from this repo's usual "duplicate rather than share" convention (that convention protects cross-service *application* code independence; this is one YAML file with zero per-service tuning called for, so a shared anchor only reduces the odds one service gets missed on a future edit). Not a dev/prod distinction, same reasoning as `restart: unless-stopped` — no overlay changes needed. Verified live: `docker inspect <container> --format '{{json .HostConfig.LogConfig}}'` confirmed `max-size`/`max-file` actually took effect on all 16 containers after `docker compose up -d --build`, including the one-shot `vault-init-permissions` init container.
- **Resource limits, now built — the last P1 security-hardening item** (item 8 in `TODO.md`). None existed before, so one runaway container (the TODO's own example: a collector stuck in a retry loop) could consume unbounded host CPU/memory. Verified first via Context7 against Docker Compose's own source (`pkg/compose/create.go`) that plain `docker compose up` (the Go-based Compose V2 CLI this repo already uses, no Swarm) directly applies `deploy.resources.limits.cpus`/`.memory` to the container — CPU *reservations* are swarm-only and ignored outside it, and since the TODO only asked for limits, reservations were left out rather than adding scope beyond what was asked. Each of the 16 services got its own hardcoded `deploy: resources: limits: {cpus, memory}` (no shared anchor this time, unlike the log-caps item — these genuinely differ per service's real workload: `postgres`/`bff` at `1.0`/`512M` as the heaviest; most Node services and the 5 Go collectors at `0.5`/`256M`; the one-shot `vault-init-permissions` init container at `0.25`/`64M`; full table and per-service rationale in this session's history) — sized as a generous circuit-breaker ceiling, not a tight capacity plan, and hardcoded rather than env-var-tunable since this is a one-time hardening pass, not a day-to-day operational dial like rate limits or backup intervals. Worst-case sum if every container simultaneously maxed out: ~9.25 CPUs / ~4.5GB (CPU oversubscription beyond physical core count is normal for limits, since CPU is schedulable rather than exhaustible the way memory is). Verified live: `docker inspect`'s `HostConfig.NanoCpus`/`HostConfig.Memory` confirmed the exact intended values landed on every one of the 16 containers after `docker compose up -d --build`, and all healthchecks/`/health` endpoints stayed green afterward.

- **Quick reference for the two overlays above** (both `--force-recreate` so containers actually pick up the new `NODE_ENV`/image, not just `--build`): to test a change end-to-end (e.g. via Playwright MCP, dev-login, or anything needing a rebuilt frontend/backend image against this environment's real data) run `docker compose -f docker-compose.yml -f docker-compose.dev.yml up -d --build --force-recreate`; the moment testing is done, restore the safe default with `docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build --force-recreate`. Never leave the stack on the dev overlay — it's the same publicly-reachable `cirrus.example.com` the whole time, just with `DEV_LOGIN_ENABLED`'s gate open.
- The frontend is wired to this — see the Frontend section above. `backend/shared-types` mirrors `frontend/src/types.ts` and is the contract both sides are expected to stay in sync with. `User.connectionIds` (alongside the pre-existing `AuthenticatedUser.connectionIds`, both from `rbac/src/lib/userDto.ts`) lets the Users & Roles drawer (`frontend/src/components/users/UserDrawer.tsx`) show and pre-check which cloud connections a Viewer can see, sending `accountConnectionIds` on `POST`/`PATCH /api/users` — only when the form's role is `viewer`; omitted for `admin` so promoting/demoting never touches existing assignments.
- `GET /api/vms`/`POST /api/vms/refresh` stream NDJSON (one `VmStreamFrame` per line — `shared-types`) instead of returning one combined JSON body, so the Inventory screen can show each provider/connection's VMs as soon as that connection's fetch settles rather than waiting for the slowest of all 5 (AWS alone can take up to 45s). The Aggregator's old `fetchAllVms` (`Promise.allSettled` + collect-after-the-fact, plus its local `FetchError` type) is gone, replaced by `fanout.ts`'s `fanOutVms(connections, forceRefresh, onResult)`, which invokes `onResult` the instant each connection's `fetchInstancesCached` call settles — success, stale-cache-fallback-with-error, or hard failure all "arrive" exactly once, `lock.ts` itself untouched. `routes/vms.ts` (`GET /vms`, `POST /vms/refresh`) calls `reply.hijack()` + writes raw NDJSON lines: a `{type:'start', connectionIds}` frame first (the full active-connection-id list, not just a count — lets consumers reconcile/prune), then one `{type:'connection', provider, connectionId, vms, error?}` frame per connection as it resolves, then `{type:'done', refreshedAt}`. The BFF (`bff/src/clients/aggregatorClient.ts`'s `streamAggregatorVms` + `bff/src/routes/vms.ts`'s `relay`/`scopeFrame`) relays this stream frame-by-frame rather than buffering it, role-scoping each `connection` frame's `vms` (empty array for a Viewer's inaccessible connection) while leaving `start`/`done` frames and a scoped-out connection's frame *existence* unscoped — same precedent as the pre-streaming route's unscoped `errors` array, so a Viewer still sees accurate overall refresh progress. `frontend/nginx.conf` has a dedicated `location /api/vms` (longer prefix than the general `/api/` block, wins automatically) with `proxy_buffering off`/`proxy_http_version 1.1`/`proxy_read_timeout 120s` — without it nginx's default buffered proxying would collect the whole chunked response before flushing it to the browser, silently defeating the streaming even though the origin streams correctly. Both `aggregator/src/routes/vms.ts` and `bff/src/routes/vms.ts` also call `reply.raw.socket?.setNoDelay(true)` right after `reply.hijack()` (Nagle's algorithm otherwise coalesces the small, frequent per-connection writes) and the aggregator writes a `{type:'ping'}` heartbeat frame (new `VmStreamFrame` variant, ignored by the BFF's scoping and by the frontend's `consumeVmStream`) every 1s while `fanOutVms` is still running, so any idle-timeout-based buffering intermediary between the origin and the browser gets more chances to flush during a slow real fetch — added after a real report of the stream arriving all-at-once in a Windows browser hitting this stack through WSL2's `localhost` port-forwarding relay (a known point where chunked responses can get buffered; verified the origin streams correctly via `curl` run *inside* the WSL2 VM, which bypasses that relay entirely). If a buffering intermediary does full-buffer-until-close rather than idle-based buffering, no app-level heartbeat fixes it — the workaround is bypassing the relay (hit the WSL2 VM's own IP — `ip -4 addr show eth0` — directly from the Windows browser instead of `localhost`) or switching WSL2 to mirrored networking mode (`.wslconfig`'s `[wsl2]\nnetworkingMode=mirrored`, Windows 11 22H2+/WSL ≥ 2.0.0).

## PRD.md

`PRD.md` is the single source of truth for this project — **Cirrus**, a Cloud VM Inventory Dashboard. Status: Approved. It is written in Bahasa Indonesia prose with English used for role names, table headers, and UI labels (this mixed convention is intentional — keep it when editing).

Key facts to know before making changes to the PRD or (later) implementing against it:

- **What it is**: an internal, read-only dashboard that aggregates VM inventory across the company's own accounts on 5 cloud providers (AWS, GCP, Alibaba Cloud, OCI, Biznet Gio Cloud) — not a multi-tenant SaaS. Avoid "customer" framing when describing cross-account auth; use "akun cloud yang didaftarkan" / "tim pemilik akun" instead.
- **Current MVP scope (§4)**: inventory list + filter/search + RBAC/SSO only. Cost/billing was deliberately cut from the MVP and moved to §10 Roadmap (with the per-provider cost-API research preserved there so it isn't lost) — don't reintroduce cost UI/flows into MVP sections (§2–§9).
- **Roles (§3)**: exactly 2 — `Admin` (manage users/roles, manage cloud account connections, view all data) and `Viewer` (view inventory for assigned accounts/projects only).
- **Auth**: Microsoft Entra ID (Microsoft 365) via OIDC, single-tenant. Identity key is `oid`+`tid` (never `email`, which is mutable).
- **Architecture (§7)**: microservices, Docker for dev / Kubernetes for prod. Frontend SPA → API Gateway/BFF → Auth Service + RBAC Service → Inventory Aggregator → 5 Provider Collectors (one per cloud, each exposing a uniform `GET /instances`). Redis caches fetch results (TTL 2–5 min, with a cache-stampede lock); PostgreSQL holds app metadata only (never live-pulled VM data).
- **Per-provider credential model (§7.3)** — deliberately different per provider, verified against current docs, don't default back to "just use an API key" for all of them:
  - GCP: Workload Identity Federation — no static secret stored at all.
  - AWS, Alibaba Cloud, OCI & Biznet Gio Cloud: static per-account credentials (IAM User Access Key / RAM User AccessKey / API Signing Key / `x-token`) in Vault KV v2 — AWS and Alibaba Cloud both deliberately moved off cross-account role assumption to this per-account model (simpler per-account setup, no hub/trust-policy, at the cost of a long-lived key vs. each provider's own recommended short-lived role assumption).
- **Tech stack (§8)**: React+TypeScript+Vite frontend; Go (using `errgroup` for collector fan-out) for Provider Collectors; Node.js/TypeScript for BFF/Aggregator/RBAC; PostgreSQL + Redis; HashiCorp Vault (KV v2); Helm umbrella chart (one subchart per microservice) for Kubernetes deploy.
