## Repository state

`PRD.md` remains the single source of truth for product scope/architecture. `frontend/` (React+TypeScript+Vite SPA per §8, ported from a Claude Design mockup `Cirrus.dc.html`) is now wired to the real backend — `frontend/src/data/mockData.ts` is gone, all data flows through `frontend/src/api/client.ts` against the BFF — and is itself now a service in `docker-compose.yml` (`nginx` serving the built SPA, proxying `/api`/`/auth` to `bff`), alongside `npm run dev` for active frontend work. `backend/` contains an MVP implementation of §7's architecture: API Gateway/BFF, Auth Service, RBAC Service, Inventory Aggregator, and all 5 Provider Collectors are built and run via Docker Compose, backed by PostgreSQL + Redis. Within that MVP, Auth Service does real Microsoft Entra ID OIDC login — still waiting on another team to create the actual Entra ID app registration, so a temporary `DEV_LOGIN_ENABLED` bypass (off by default) exists to exercise the full app in the meantime. **All 5 Provider Collectors now make real API calls** — AWS (static per-connection IAM Access Key/EC2 — no hub account, no AssumeRole, see below), Alibaba Cloud (static per-connection RAM User AccessKey/ECS — no hub account, no AssumeRole either, same model as AWS, see below), GCP (Workload Identity Federation/Compute Engine), OCI (API Signing Key/Core Compute across all accessible compartments and, since the region auto-discovery change below, every region the tenancy subscribes to), and Biznet Gio Cloud (plain REST, `x-token`, both NEO Lite/NEO Lite Pro product lines) — verified to compile and fail gracefully against real SDKs/real endpoints (OCI additionally confirmed reaching OCI's real Identity API and getting a genuine rejection back). **All 5 Provider Collectors are now confirmed against real successful fetches** — a real Biznet connection returned real instance data, which exposed several field-mapping mismatches now fixed in `mapInstance` (see Backend section below); a real AWS account with 2 registered connections instead exposed a timeout/graceful-degradation bug (the collector's flat 20s all-or-nothing deadline for a real multi-region EC2 fetch, plus a bug that silently dropped a region's instances entirely if only its disk lookup timed out) now fixed (see Backend section below); a real OCI tenancy full of running instances instead exposed a hard crash on every Refresh despite a passing `/test` — the collector's boot/block volume attachment lookup omitted the `AvailabilityDomain` parameter OCI's SDK marks mandatory, so the request failed locally before ever reaching OCI's network, and since that lookup runs for any compartment with ≥1 instance and one compartment's failure aborted the whole fetch, this was a 100%-reproducible failure for any real tenancy — now fixed (see Backend section below); GCP (real Compute Engine instances via a real project's Workload Identity Federation setup) and Alibaba Cloud (real ECS instances via a real RAM User AccessKey) both returned real instance data on the first real attempt, with no code changes needed — GCP's lightweight `/test` path (WIF exchange only) had already been confirmed against a real project earlier, which surfaced and fixed a token-source caching bug (see Backend section below). **VM detail's Storage section now shows provider-native disk labels instead of purely synthetic ones** — AWS EC2/GCP/OCI all already fetched a real per-disk identifier (device path, named resource, or `DisplayName`) as part of calls they were already making, just discarding it during mapping; Alibaba fetched no disk data at all before this and gained a new per-region `ecs:DescribeDisks` call to get any. Every provider's disk label is now `"<Role> (<real identifier>)"` (e.g. `"Root (/dev/sda1)"`, `"Data 1 (persistent-disk-1)"`), falling back to the bare role when no identifier is available — never an empty-parens label. Role terminology is deliberately unified to `"Root"`/`"Data N"` across all 5 providers rather than each provider's own native term (AWS says "root", GCP "boot", OCI "boot", Alibaba "system") — this changes OCI's boot-volume role label from `"Boot"` to `"Root"`, the one visible behavior change in this pass beyond adding identifiers. Alibaba's new `DescribeDisks` call is deliberately more lenient on error than its neighboring `DescribeInstances` call in the same per-region fan-out — any failure (not just a timeout) degrades to keeping that region's instances without disk info, since an existing connection's RAM policy predates this new call and a fresh `AccessDenied` on it is the expected first-contact experience, not a real fetch failure. Biznet is unchanged — its real API payload was confirmed to expose only a single aggregate `disk_size` number with no per-disk name/device field, so it keeps its literal `"Root"` label. **This surfaced a real, previously-invisible AWS EC2 bug, now fixed**: `describeVolumesByInstance` (`collectors/aws/internal/instances.go`) used to label whichever volume `DescribeVolumes` happened to return first as `"Root"` — that return order is not documented or guaranteed to put the boot volume first, so a real instance was seen mislabeling its actual root disk (`/dev/sda1`) as `"Data 1"` and a data disk (`/dev/sdb`) as `"Root"`. The old label was wrong exactly as often before this pass too, it just said generic `"Root"`/`"Data 1"` with no device name attached, so the mistake had no visible symptom until a real device path was shown next to it. Fixed by matching each volume attachment's `Device` against the owning instance's own `RootDeviceName` (`ec2types.Instance.RootDeviceName`, already present in the `DescribeInstances` response `describeAllInstances` already fetches — no new API call) instead of array position; falls back to the old first-attachment guess only if no attachment's device matches (root device name unknown, or an older Xen-based instance where the kernel-visible device can legitimately differ from what EC2 reports). **HashiCorp Vault (KV v2, production mode — file storage backend, persists across restarts) backs OCI's/Biznet's/AWS's/Alibaba's per-connection secrets** (RBAC is the sole Vault client, authenticating with a least-privilege token scoped to `cirrus/connections/*` rather than the root token; verified round-tripping a real per-connection secret split/merge/cleanup). The Helm/Kubernetes deploy path (§8) is still not built — this pass uses Docker Compose only. **The periodic (§6.1, every 6h by default) connection health-check background job is now built** — `POST /api/connections/:id/test` (manual, on-demand) is joined by an in-process scheduler inside `rbac` that runs the same check against every stored connection automatically (see Backend section below for detail).

## Frontend (`frontend/`)

- Tech stack matches PRD §8: React + TypeScript + Vite; `oxlint` for linting (`npm run lint`); `tsc -b && vite build` for the build.
- State: a single `useCirrusApp()` hook (`src/state/useCirrusApp.ts`) holds all app state/actions — no external state library (Redux/Zustand etc.). Keep new state co-located there rather than introducing a second state mechanism.
- Styling: CSS variables per theme + component classes in `src/index.css`, not inline style-string builders (that was the source mockup's approach, deliberately not carried over). Dynamic/data-driven colors (provider brand colors, status colors) stay as inline `style`.
- Theme default: light mode. `src/state/useCirrusApp.ts`'s `theme` state initializes from `localStorage` (`getInitialTheme()`, key `cirrus-theme`, falling back to `'light'` if unset/invalid) and a `useEffect` persists every `setTheme` call back to that same key — added after a real bug where both login paths (`window.location.href` to `/auth/login` or `/auth/dev-login`, see Backend section) do a full browser navigation, so the Auth Service's post-login `reply.redirect()` back to the SPA root remounted React and silently reset an in-memory-only theme choice to light. Still no OS-preference (`prefers-color-scheme`) detection.
- Data: no more mock data file — `src/api/client.ts` holds typed fetch wrappers for every BFF route, and `src/state/useCirrusApp.ts` is fetch-driven (bootstraps the session via `GET /auth/me`, then loads `providers`/`vms`/`connections`/`users` from the backend; `providers` now carries `fieldDefs`/`setupGuide`/`failureMessage` per-provider, replacing the old static `FIELD_DEFS`/`CHECKLIST`/`FAILURE_MSG` maps from PRD §7.3 — the wizard step-2 side card renders `setupGuide` under the heading "How to get these values", provider-specific instructions for obtaining the credential values from each provider's own console, not a list of API calls Cirrus makes to verify them; GCP's card additionally renders a "Download cirrus-jwks.json" button, `wizardProviderMeta?.id === 'gcp'`-gated, that's just a plain `<a href="/api/gcp/jwks" download>` — same-origin so the session cookie rides along automatically, no `api/client.ts` fetch wrapper needed — since GCP's Workload Identity Federation needs that file uploaded manually, see Backend section). Always fetch relative paths (`/api/...`, `/auth/...`), never an absolute `localhost:8080` URL — both the Vite dev server (`vite.config.ts`'s `server.proxy`) and the built container's nginx (`nginx.conf`) proxy those same relative paths to the BFF, so the identical bundle works unmodified in either mode. The two run on the same host port (5173) by convention — never both at once.
- Routing is real, not a `screen`-state switch: `src/router.tsx` defines a code-based TanStack Router (`@tanstack/react-router`) route tree — `/` (login, redirects to `/inventory` if already authenticated), and a protected layout route (redirects to `/` if not authenticated) with children `/inventory`, `/connections`, `/connections/new` (the add-connection wizard), `/users` (the latter three additionally guarded admin-only via `beforeLoad`, mirroring `Sidebar.tsx`'s nav-item visibility but enforced even on a direct URL visit). `App.tsx` still calls `useCirrusApp()` once and only mounts `<RouterProvider router={router} context={{ app }} />` after `authChecked` — this defers every route guard until the async session check resolves, avoiding a race, and is the documented TanStack pattern for injecting hook-derived context into a router created once at module scope. `useCirrusApp.ts` no longer holds a `screen` state at all; navigation goes through `router.navigate(...)` (confirmed via Context7 to work imperatively from a plain hook, not just inside components) or `<Link>` (used in `Sidebar.tsx`, with `activeProps` driving the nav-item highlight that `screen === X` checks used to do). `AppShell.tsx` is now just `ProtectedLayout` (Sidebar + an `<Outlet/>`) plus a small `ScreenLayout` helper each route's page component wraps itself in — a single `<Outlet/>` can only render one matched component, so header+body per screen can no longer be split across two containers the way the old `screen`-switch did.
- **`context={{ app }}` on `RouterProvider` is for `beforeLoad` guards only, never for rendering** — this was a real bug, not a hypothetical: route page components originally read the live `app` via `xxxRoute.useRouteContext()`, but TanStack Router only recomputes route context on a fresh match (navigation or `router.invalidate()`), so it doesn't reactively pick up state changes from clicks between navigations — confirmed via Context7 against TanStack's own docs/GitHub issues. Symptom was silent: clicking "Invite User" or a Connection card did nothing, yet the state change *had* happened — navigating away and back would reveal a drawer that was already open. Fixed by adding `src/state/AppContext.tsx` (a plain `createContext`/`useApp()` pair), providing it in `App.tsx` via `<AppContext.Provider value={app}>` wrapping `<RouterProvider>`, and switching every route page component plus `ProtectedLayout` from `useRouteContext()` to `useApp()` for rendering. `beforeLoad`/`requireAdmin` still correctly read `context.app` — that per-navigation guard use was never broken. If a new route page component is added, give it `useApp()`, not `useRouteContext()`.
- The Sidebar's old "Preview role" toggle, Inventory's old "Preview" (loading/empty/outage) toggle, and Connections' old "Preview: Default/Empty" toggle are all gone by design, not an oversight — once role and fetch state are server-driven, a client-side override of any of them would just lie to the user. Don't re-add them; if a design-preview mode is needed again, it should be a clearly-labeled dev-only affordance (see the `import.meta.env.DEV`-gated "Dev login" button in `LoginScreen.tsx` for the pattern), not a first-class UI control.

- Provider icons are bundled locally under `src/assets/providers/` (not hotlinked). Note for future icon updates: brandfetch's CDN blocks hotlinking without browser-like `User-Agent`/`Referer` headers on `curl`.
- `Toast` (`src/components/shared/Toast.tsx`) is self-animating, not parent-mounted/unmounted: it owns its own `phase` (`'entering' | 'exiting' | null`) state, so when `app.toast` clears it animates out (slide+fade, `toastOut` keyframe) for 200ms before actually unmounting, instead of vanishing instantly. Positioned bottom-right with equal margins (`bottom: 10px; right: 10px` in `index.css`, slide direction flipped to match) — it used to be bottom-center with no animation, then briefly top-right (`top: 88px`, offset below the 72px per-screen header row) to avoid overlapping header action buttons (Invite User, Add Connection, etc.), before settling on bottom-right; `10px` (not the more typical `24px`) so it clears the last row of a full-height Inventory table instead of overlapping it.
- Docker: `frontend/Dockerfile` is a multi-stage build (`node:24-alpine` → `nginx:stable-alpine`) per PRD §7's "Docker for dev" — keep base images current stable/LTS when touched, don't quietly pin to whatever the scaffold generated. It's wired into the root `docker-compose.yml` as the `frontend` service (port `5173:80`, `depends_on: bff`). Its healthcheck probes `http://127.0.0.1/`, not `http://localhost/` — `nginx` binds `0.0.0.0:80` only (IPv4), but `localhost` resolves to `::1` first inside the container, so `wget` hit "connection refused" on every single probe despite the site itself working fine, permanently marking the container `unhealthy`. This isn't just cosmetic: Traefik (the external reverse proxy fronting `cirrus.example.com`, config outside this repo) excludes `unhealthy` containers from routing entirely, so this alone took the public dashboard down with a bare Traefik-level 404 (no matching router) even though every backend service was otherwise fine.
- Inventory's initial load and Refresh button no longer wait for every provider before showing anything: `GET /api/vms`/`POST /api/vms/refresh` are NDJSON streams (one JSON frame per line — `start`/`connection`/`done`, `VmStreamFrame` in `shared-types`/`types.ts`), not a single combined response — see Backend section below for the server side. `useCirrusApp.ts` holds `vmsByConnection`/`vmErrorsByConnection` (`Map<connectionId, ...>`) instead of flat `vms`/`vmErrors` arrays; `vms`/`vmErrors` are now derived (`useMemo`) by flattening those maps, so nothing downstream (`InventoryScreen.tsx`, filters, stats) needed an interface change. `consumeVmStream` (shared by the bootstrap effect and `refreshInventory`) updates one connection's slice of the maps per `connection` frame as it arrives and tracks a `vmProgress: {done, total} | null` used to render a "Refreshing X/Y connections…" indicator next to the Refresh button (`InventoryHeader` in `InventoryScreen.tsx`) — deliberately "connections" not "providers" in the copy, since a provider can have more than one registered connection (e.g. AWS with 2). The `start` frame carries the full current `connectionIds` list (not just a count), which `consumeVmStream` also uses to prune any connection deleted since the last load out of both maps immediately, so a removed connection's VMs don't linger. `InventoryScreen.tsx`'s full-table skeleton (`showSkeleton`) now only shows when `vms.length === 0` — once the first connection frame lands the table renders and later frames update rows in place, no more blank-whole-table-until-everything-finishes. The bootstrap effect's stream is cancellable (`AbortController`, `getVmsStream`'s optional `signal` param) so React StrictMode's dev-mode double-effect-invocation aborts the stale run instead of leaving two overlapping streams racing on the same state; `refreshInventory` doesn't need this since it's click-triggered (can't be StrictMode-doubled) and already guards re-entrant clicks via `vmProgress`.

- **Connections screen crash, fixed.** Discovered live in production (via Playwright, while verifying the P1 security-headers change) — `ConnectionsScreen.tsx` crashed with `TypeError: Cannot read properties of undefined (reading 'name')` on every real connection at once. Root cause was a load-order race, not a provider-id mismatch: the bootstrap effect in `useCirrusApp.ts` fires `getProviders(true)` and `loadConnections()` as two independent, unawaited fetches, and there was a `connectionsLoading` state but no `providersLoading` one — so if `GET /api/connections` resolved before the (heavier) `GET /api/providers?includeFieldDefs=true` call, `ConnectionsScreen.tsx`'s `showLoading` (gated only on `connectionsLoading`) flipped `false` while `app.providers` was still `[]`, and every row's `providerMap[c.provider]` lookup came back `undefined` simultaneously. `useCirrusApp.ts` now has a real `providersLoading` state (same `.finally()` convention as `connectionsLoading`/`usersLoading`), and `ConnectionsScreen.tsx`'s `showLoading` is `app.providersLoading || (app.connectionsLoading && connectionsRows.length === 0)` — deliberately not gated behind `connectionsRows.length === 0` alone, since that's exactly the condition that let a non-empty connections list race ahead of an empty provider map. Separately, as defense-in-depth against a genuine (not just racy) `GET /api/providers` failure — there's no `providersError`/retry state for it today, just a toast, so `providers` can stay `[]` forever — `ProviderBadge.tsx`'s `provider` prop and `ConnectionCard.tsx`'s `providerMeta` prop are now `| undefined` with a neutral fallback (muted badge, "Unknown provider" label) instead of an unguarded `.name`/`.bg` read; `EditConnectionDrawer.tsx` had the identical unguarded pattern (a `!` compile-time-only assertion immediately followed by an unguarded `.name`, despite already correctly using `?.fieldDefs ?? []` two lines earlier in the same function) and got the same fix.
- **VM Inventory table now supports column sorting**, all 10 columns (Name, Provider, Account, Region, Status, Type, CPU, Memory, Disk, IP). `useCirrusApp.ts` holds `sortColumn`/`sortDirection` (`VmSortColumn | null`/`'asc' | 'desc'`) plus a `toggleSort(column)` handler, as a view preference deliberately independent of the filter state above it — not reset by `clearFilters`, and persists across `refreshInventory`/navigation exactly like `search`/`filterProviders` already do. Click cycle is 2-state per column (unsorted → ascending; active column toggles asc↔desc; switching to a different column always restarts at ascending — no per-column direction memory). `InventoryScreen.tsx`'s `compareVms` comparator always returns "ascending" ordering (the direction flip is applied once, generically, by the caller) and handles the 3 non-obvious columns deliberately: Status ranks via an explicit `{running: 0, stopped: 1}` map rather than alphabetically (so a future third status can't accidentally rank oddly); Disk sorts by the *sum* of all of a VM's `disks[].sizeGB` (total storage), not just the first disk; IP sorts by `privateIp` (the visually primary value in that merged column), with VMs missing one always sorted last regardless of direction. The `sorted` `useMemo` runs *before* `rows`' `.slice(0, 100)` — sorting only the already-truncated 100 rows would just reorder a filter-order-dependent subset instead of actually surfacing e.g. the real highest-CPU VM if it's outside the first 100. `VmTable.tsx`'s headers are now a mapped `COLUMNS` array of clickable `<th>`s carrying a caret `<svg>` (the same chevron path already used in `FilterDropdown.tsx`) and `data-sorted`/`data-direction` attributes, mirroring the `data-open`/`data-selected` convention `.filter-trigger` already established — a currently-untouched header shows its caret at low opacity for discoverability, full opacity on the active column, rotated for ascending (the convention landed on: ascending = ▲ up, descending = ▼ down, matching Excel/Notion/Airtable). Needed a `white-space: nowrap` on `.th-sortable` too — a narrow column (Memory, whose cell content is a short "64 GB") otherwise wrapped its label and caret onto two lines instead of forcing the column wide enough for both on one line.
- **Column drag-resizing (both the Inventory and Users & Roles tables) has been removed in favor of fixed-width columns, word-wrap, and horizontal scroll.** The earlier drag-to-resize feature (a shared `frontend/src/lib/columnResize.ts` hook, per-column `localStorage`-persisted override maps, `.th-resize-handle` drag handles) is gone entirely — columns no longer have a fluid/percentage default or a user-adjustable width at all. `VmTable.tsx`'s `COLUMNS` and `UsersScreen.tsx`'s `USER_COLUMNS` now carry a literal fixed `width` (px) per column instead, sized generously enough that realistic values fit on one line (e.g. Inventory's Account column at 245px comfortably fits a full email address; Type at 150px covers OCI's `VM.Standard.E5.Flex`) — these are a tuned starting heuristic, not a guarantee for every possible value. `.td` in `index.css` switched from `overflow: hidden; text-overflow: ellipsis` (truncation) to `white-space: normal; overflow-wrap: anywhere` (word-wrap), so any value longer than its column wraps onto additional lines instead of ever being cut off with "…" — `overflow-wrap: anywhere` specifically because values like AWS ARNs have no natural break points. `.cirrus-table` still uses `table-layout: fixed` with an unstyled trailing spacer `<col>` that absorbs leftover width on a wide desktop viewport (unchanged from before), but the same fixed-table-layout algorithm (CSS 2.1 §17.5.2.1: a table's rendered width is `max(specified width, sum of column widths)`) now also handles the opposite case for free — on a viewport too narrow for the sum of fixed column widths, the table renders wider than its container instead of shrinking any column, and the existing `overflow: auto` ancestor div both tables already wrapped their `<table>` in scrolls horizontally to reveal the rest. No new JS/media-query logic was needed for this. `VmSortColumn` stays (Inventory's column-sorting feature is untouched); `UserColumnKey`/`COLUMN_KEYS`/`USER_COLUMN_KEYS`/`MIN_COLUMN_WIDTH` were all dead once the override-map validation that was their only consumer went away, and have been deleted.
- **Users & Roles table now also supports column sorting**, all 3 columns (User, Role, Last login) — closing the gap with Inventory's own per-column sort. New `UserSortColumn` type (`frontend/src/types.ts`) plus a separate `userSortColumn`/`userSortDirection`/`toggleUserSort` state triplet in `useCirrusApp.ts` (kept independent from Inventory's own `sortColumn`/`sortDirection`/`toggleSort` since it's a different table; same 2-state click-cycle behavior, defaulting to sorting by name ascending). `UsersScreen.tsx` gained `compareUsers`: `user` sorts by name via `localeCompare`, `role` via an explicit admin-before-viewer rank map (mirrors Inventory's Status column using a rank map instead of alphabetical order for a small closed enum), `lastLogin` via numeric timestamp comparison with an unparseable value (the literal `"Never"` string some users have) pushed last regardless of direction (mirrors Inventory's IP column missing-value handling). The sortable `<th>` markup (caret `<svg>`, `data-sorted`/`data-direction`) is copied verbatim from `VmTable.tsx` — no new CSS needed, `.th-sortable`/`.th-sort-caret` were already shared/generic. While touching this, `USER_COLUMNS`' fixed pixel widths were also retuned wider (User 340px / Role 130px / Last login 220px) after a brief detour through percentage widths surfaced a real bug worth noting: on a narrow viewport, a percentage-width column has no floor, so it can shrink below a badge's natural content width, and `overflow-wrap: anywhere` then breaks that content character-by-character (e.g. "Admin" wrapping into a vertical single-letter stack) since a short word like that has no natural break point. Reverted to fixed pixel widths (same mechanism as the bullet above) specifically because a column's rendered width then never shrinks below its design regardless of viewport — a narrow viewport instead overflows the whole table into horizontal scroll, matching Inventory's behavior exactly, at the cost of reintroducing a visible trailing-blank-space on a wide desktop screen (the same spacer-column tradeoff the bullet above already describes) — an accepted tradeoff since 3 narrow fixed columns can't help but leave more of that gap than Inventory's wider 10-column spread does.

## Backend (`backend/`)

- npm workspaces monorepo: `shared-types` (mirrors `frontend/src/types.ts` — keep these in sync, it's the frontend-facing contract), plus `bff`, `auth`, `rbac`, `aggregator` — all Fastify services in TypeScript, run via `tsx` in dev and compiled (`tsc -b`) in their Docker images.
- `collectors/` is a *separate* Go workspace (`go.work`, not part of the npm workspace): `internal-kit` (shared HTTP envelope and RBAC-config-fetch helpers only — `rbacclient.go`'s `GetConnectionConfig` is used identically by every real collector, but carries zero provider-specific logic itself; the old deterministic fake-fleet generator (`stub.go`) from before every collector made real API calls has been deleted — no dead stub-generation code left) plus one independent module per provider (`aws/`, `gcp/`, `alibaba/`, `oci/`, `biznet/`) — each its own binary/container so a failure or bad release in one never affects the others (PRD §7.1's isolation goal).
- Service ownership boundaries: `rbac` is the *sole* owner of PostgreSQL (users, cloud connections, audit log — schema in `rbac/src/db/schema.ts`, Drizzle ORM); `aggregator` is the *sole* owner of Redis (per-`(provider, connectionId)` cache with a `SET NX PX` stampede lock, `aggregator/src/cache/lock.ts`); `bff` is the only service meant to be called from outside the Docker network and proxies/aggregates the others.
- Auth is real, not stubbed: `auth/` performs actual Microsoft Entra ID OIDC (Authorization Code + PKCE via `@azure/msal-node`), single-tenant, identity keyed on `oid`+`tid` per PRD §3. It mints its own ES256 JWT (via `jose`) and exposes a JWKS endpoint (`/.well-known/jwks.json`) that `bff` verifies sessions against. Needs real Entra ID app registration values (`ENTRA_TENANT_ID`/`ENTRA_CLIENT_ID`/`ENTRA_CLIENT_SECRET`) in `.env` — everything else in the stack works without them.
- `auth/src/oidc/callback.ts`'s `/callback` route is hit via a top-level browser redirect from Microsoft (not a fetch/XHR), so it never returns raw JSON on failure — every error branch (`INVALID_FLOW`/`STATE_MISMATCH`/`OAUTH_ERROR`/`NETWORK_ERROR`/`MISSING_CLAIMS`/`NOT_INVITED`/`RBAC_UNAVAILABLE`) redirects back to `POST_LOGIN_REDIRECT` with `?authError=<code>` via the shared `redirectWithError` helper (`auth/src/oidc/errorRedirect.ts`, also used by `devLogin.ts`); the frontend's login route (`frontend/src/router.tsx`'s `loginRoute`) reads that param via `validateSearch`, maps the code to a human message, shows it as a red-variant `Toast` (`Toast`/`showToast` now take an optional `'success' | 'error'` variant, default `'success'`, in `frontend/src/state/useCirrusApp.ts`/`frontend/src/components/shared/Toast.tsx`), then strips the query param via a `replace: true` navigation. - Vault is real, not deferred, and runs in **production mode** (not dev mode — switched after a real incident where a live AWS connection's `secretAccessKey` was silently lost on a `vault` container restart, since dev mode is in-memory only): the `vault` service (`hashicorp/vault`) boots via a custom `vault/entrypoint.sh` (bind-mounted, replaces `command: server -dev`) that starts `vault server -config=/vault/config/config.hcl` (`vault/config.hcl` — `storage "file"` at `/vault/file`, backed by the `vault-file` named Docker volume so it persists across restarts like `pgdata` does; `disable_mlock = true` since the custom entrypoint bypasses the image's own root→vault `setcap cap_ipc_lock` step; `listener "tcp" { tls_disable = 1 }`, consistent with every other inter-service call in this stack being plain HTTP inside the Docker network). On first boot the entrypoint runs `vault operator init` (5 Shamir key shares / 3 threshold) and persists the unseal keys + initial root token into `/vault/init/.cirrus-init/init.txt`, backed by a dedicated `vault-init` Docker volume — **deliberately separate from `vault-file`**, after a production-readiness review flagged that the original design (this file lived at `/vault/file/.cirrus-init/init.txt`, inside the same volume as Vault's own encrypted data) defeated Shamir separation-of-duty in practice: anyone with access to that one volume got both the lock and the key. The entrypoint also no longer `echo`s the raw `vault operator init` output to container stdout — it's written straight to the file (`chmod 600`) and only a pointer message prints, since the original design left the keys retrievable indefinitely from `docker compose logs vault`. A one-time migration block moves an already-initialized deployment's pre-existing `/vault/file/.cirrus-init/init.txt` into the new volume automatically on its next restart, no manual steps needed — though rotating/purging the root token + unseal keys already exposed in *this* environment's pre-fix log history is a manual operational step outside code's reach. That `vault-init` volume split introduced a real first-boot bug of its own, hit on this environment's first production bring-up: unlike `vault-file`, whose path is baked into the `hashicorp/vault` image (already owned by `vault:vault`, so Docker copies that ownership into a freshly created named volume), `vault-init` is a path the image has never heard of — a brand-new named volume mounted there comes up owned by `root:root`. `entrypoint.sh` runs entirely as the image's non-root `vault` user (uid 100/gid 1000 — see the `disable_mlock` note above for why there's no root step at all), so it can't `mkdir`/write into a root-owned mountpoint; the stock image's own `docker-entrypoint.sh` would normally `chown` a path like this, but only when invoked as `vault ...`, and our command is `sh /vault/entrypoint.sh`, so that logic never fires. Worse, `entrypoint.sh` has no `set -e`, so the failed `mkdir` didn't stop the script — `vault operator init` still ran and generated a real Shamir key set, which then failed to write to disk, sealing the backing store with unseal keys that were never persisted anywhere (unrecoverable; required wiping `vault-file`+`vault-init` and re-initializing from scratch). Fixed with a one-shot `vault-init-permissions` service (`docker-compose.yml`, same `hashicorp/vault` image, `user: root`, `entrypoint: chown -R 100:1000 /vault/init`) that `vault` now `depends_on` with `condition: service_completed_successfully` — deliberately an init-container-style fixup rather than making the main `vault` service itself run any part of its startup as root. On *every* boot (first or not) the entrypoint re-unseals from that file, enables the `secret/` KV v2 mount, writes a least-privilege `cirrus-rbac` policy (`secret/data/cirrus/connections/*` create/read/update/delete, `secret/metadata/cirrus/connections/*` delete), and mints RBAC's actual token pinned to the `VAULT_TOKEN` value from `.env` (passed into the vault container as `CIRRUS_RBAC_TOKEN`, deliberately not `VAULT_TOKEN`, so the vault CLI doesn't try to auth with a token that doesn't exist yet) — no renewal job, `-ttl=87600h` (~10 years), same operational shape as this project's other long-lived static secrets (`INTERNAL_SHARED_SECRET`). `vault/healthcheck.sh` gates the Docker healthcheck on a bootstrap sentinel file, not just `vault status`, so `rbac` (which `depends_on: vault: condition: service_healthy`) never starts against a half-provisioned Vault. This backs `rbac/src/lib/vault.ts`, the *only* Vault client in this stack (plain `fetch` against the KV v2 HTTP API, no client library, unchanged by this switch). `FieldDef.secret` (`rbac/src/data/providers.ts`) marks which per-provider fields actually need Vault — today OCI's `privateKey`/`passphrase`, Biznet's `xToken`, AWS's `secretAccessKey`, and Alibaba's `secretAccessKey`; GCP's fields are all non-secret identifiers and never touch Vault, and AWS/Alibaba's own `accessKeyId` fields are likewise non-secret (only each provider's secret key is Vault-backed). `connections.ts`'s create/update routes split incoming `config` accordingly (non-secret → Postgres as always, secret → Vault at `cirrus/connections/{id}`, path stored in `secret_ref`); delete cleans up the Vault entry too. `internal.ts`'s collector-facing config endpoint merges the Vault secret back into `config` transparently, so a collector never knows or cares whether a field came from Postgres or Vault. - **Internal TLS — decided: accept the risk, documented, not built** (P1 security hardening item 5 in `TODO.md`). `docker-compose.yml`'s `networks:` section shows the real topology: only `frontend` joins the external `proxy` network Traefik lives on; every other service — `bff`/`auth`/`rbac`/`aggregator`/all 5 collectors/`postgres`/`redis`/`vault` — has no explicit `networks:` key, so they all implicitly share one flat Compose `default` bridge network on a single Docker host. Given that shape, the realistic attack path internal TLS protects against is a network sniffer positioned *between* two containers on that same bridge — reaching that position already requires root on the host or code execution inside another container with raw-socket access, at which point a sniffer could equally well read `INTERNAL_SHARED_SECRET` off the wire (sent as a plain header today) and impersonate a service anyway, so TLS's marginal benefit here is real but narrower than it first sounds. Cirrus also handles cloud credentials (Vault-encrypted at rest) and VM inventory metadata for an internal company tool, not data under a compliance regime that mandates encryption-in-transit internally. A specific alternative was raised and ruled out before landing on this decision: reusing Traefik's existing Let's Encrypt cert for Vault's listener (`tls_disable = 1` in `vault/config.hcl`) doesn't work — that cert is issued via ACME for the public domain (`cirrus.example.com`/`*.example.com`) and can't include the internal Docker hostname (`vault`) in its SAN list, so standard TLS hostname verification would fail even if the cert file were reachable, which it isn't anyway (Traefik's config and cert storage are external to this repo). The real alternative — a self-signed internal CA issuing a cert for the `vault` hostname specifically, HashiCorp's own recommended pattern for Vault — is genuine, ongoing PKI work (manual issuance/rotation, no Let's-Encrypt-style auto-renewal) judged disproportionate for this single-host deployment once that cost was made concrete. This is an explicit, not permanent, acceptance — revisit if the deployment ever goes multi-host or a compliance requirement appears.
- **Backup procedure for Postgres + Vault, now built** (P1 security hardening item 6 in `TODO.md`) — previously no backup/restore mechanism existed for either. Two new sidecar services, `postgres-backup`/`vault-backup` (`docker-compose.yml`), each a stock base image running a bind-mounted hand-rolled sleep-loop script (`backup/postgres-entrypoint.sh`/`backup/vault-entrypoint.sh` — same "no cron-expression library" convention as `rbac/src/scheduler.ts`): dump/archive → prune backups past `*_RETENTION_DAYS` → sleep `*_INTERVAL_SECONDS` → repeat, defaults daily/1 week. Output goes to a **host bind-mounted** `./backups/postgres`/`./backups/vault` (gitignored), not a Docker-managed volume, so it's trivially copyable off the host (rsync/cloud-sync — that off-box shipping step itself stays a manual/external operational task, same precedent as the P0 Vault fix leaving root-token rotation manual). `postgres-backup` is the same `postgres:17-alpine` image as the real `postgres` service (keeps `pg_dump`'s version matched to the server) and connects over the network (`pg_dump -h postgres`) rather than touching the `pgdata` volume directly, so a corrupted/lost `pgdata` can't take the backups down with it. `vault-backup` is `alpine:3.22` tarring a **read-only** mount of `vault-file` — the only backup method the file storage backend actually supports (no hot-backup API, unlike the Raft backend's `vault operator raft snapshot`, which doesn't apply since this deployment uses `storage "file"`); a real, stated caveat is that this is a filesystem-level snapshot of a live Vault, not an atomic backend-native export, so a backup could in theory land mid-write — accepted for this deployment's low-write-throughput pattern (connections created/edited rarely). **`vault-init` (the unseal keys/root token) is deliberately never backed up by either script** — that volume's content is meant to be extracted once into a password manager per the existing bootstrap docs, and auto-copying root credentials to another on-host location would widen exposure, not reduce it; this also directly satisfies the TODO item's "decoupled from wherever the unseal keys end up" requirement, since Vault's actual backup never shares a location with them. Both scripts capture their dump/tar command's exit status explicitly (not via shell pipefail, since Alpine's `/bin/sh` is `busybox ash`) before atomically renaming a `.tmp` file into place, and `chmod 600` every written file. Verified live end-to-end: both wrote a valid file on first boot (`gzip -t`/`tar -tzf` both clean); the Postgres dump was fully restored into a throwaway `postgres:17-alpine` container and confirmed real row counts back (`users`/`cloud_connections`/`audit_log`); the Vault tar was extracted into a scratch directory and confirmed to contain exactly Vault's file-backend layout (`core/`/`logical/`/`sys/`) with no `.cirrus-init`/unseal-key material present; retention pruning confirmed by seeding a manually-aged dummy file and observing it (and only it) get deleted on the next cycle.

- **Self-removal on Users & Roles, fixed — surfaced by a real incident where removing your own admin account showed a blank, green (success-styled) toast instead of an error.** Root cause was a chain, not a single bug: `routes/users.ts`'s `DELETE /users/:id` had no guard against the acting user deleting themselves, and `cloud_connections.added_by_user_id`/`audit_log.actor_user_id` (`db/schema.ts`) both `.references(() => users.id)` with no `onDelete` rule — so any user with prior history (an invite sent, a connection added) threw an uncaught Postgres FK-violation on delete, not just on self-delete. That reached `bff`/`auth`/`rbac`/`aggregator`'s shared `setErrorHandler`, which sent 5xx/4xx bodies as `{error: 'a string'}` instead of this API's usual `{error:{code,message}}` shape; the frontend's `client.ts` couldn't extract a message from that shape and fell through toward an empty string, and `useCirrusApp.ts`'s `errorMessage()` trusted that empty `ApiError.message` instead of using its `fallback` argument — landing on `showToast('')`. Separately, `removeUser`'s (and `removeEditConnection`'s) catch block never passed `'error'` as `showToast`'s variant, so even a correct message would have rendered in the default green/success style. Fixed at every layer: `routes/users.ts` now 400s with `{code:'CANNOT_REMOVE_SELF'}` before touching the DB when the `x-actor-user-id` header matches the target id; both FK columns got `{onDelete: 'set null'}` (a connection/audit entry should outlive the user who created/performed it) via a new Drizzle migration; all 4 services' error handlers now always emit `{code,message}`; `errorMessage()` falls back on a falsy message; and both `removeUser`/`removeEditConnection` now pass `'error'`. - **"Last remaining admin" guard, now built — a direct follow-up to the self-removal fix above, from asking "should the bootstrap admin be deletable at all?"** Before this, only self-deletion was blocked; a *different* admin could freely delete or demote (to Viewer) any other admin, including the very last one, leaving the system with zero admins and nobody left who could invite/manage users. This is a general rule, deliberately **not** specific to the seeded bootstrap admin's identity — it applies equally to any admin, seeded or invited. `routes/users.ts` gained a `countAdmins()` helper (`.select().where(eq(users.role,'admin'))` then `.length` — matches this codebase's existing convention of no `count()`/`sql\`count(*)\`` helper anywhere), and both `DELETE /users/:id` and `PATCH /users/:id` now check it: `DELETE` 409s with `{code:'LAST_ADMIN'}` if the target is an admin and `countAdmins() <= 1`; `PATCH` runs the identical check only when the request body's `role` is explicitly `'viewer'` (so ordinary name/email/connection edits pay no extra query) and the target's *current* role is admin. Self-demotion isn't separately blocked — the invariant is "at least one admin must exist," not "you can't touch your own role," so an admin demoting themselves is fine as long as another admin remains. `UserDrawer.tsx` mirrors this proactively, the same "UI guard + backend guard" pattern as the self-delete fix: computes `adminCount`/`isLastAdmin` from `app.users` (already loaded client-side, no new API call), hides "Remove User" and disables the "Viewer" role pill (with an inline hint) when editing the system's only remaining admin — the backend 409 stays as defense-in-depth for e.g. a race between two admins acting at once. `isLastAdmin` deliberately reads the target's role off `app.users` (the last-saved server state), not off `app.userForm.role` (the in-progress, unsaved form selection) — an earlier version read the form value and had a real bug caught live via Playwright: tentatively selecting "Admin" for a currently-Viewer user (a promotion, always safe) flipped `isLastAdmin` on before Save was even clicked, incorrectly disabling that same drawer's own Viewer pill mid-edit. **Deliberately left unchanged**: `db/seed.ts`'s bootstrap-admin re-creation. It re-inserts `SEED_ADMIN_EMAIL` on every `rbac` container start if that email is missing from `users`, regardless of how many other real admins currently exist — confirmed via code read, not a guess. This is intentional, not a bug to "fix": it's the system's own recovery safety net for the scenario where every admin account has somehow been lost (e.g. a botched migration, an Entra ID tenant issue locking out all real admins) — restarting `rbac` always restores at least one known-email admin to regain access. A real, accepted consequence: deleting the bootstrap admin while other real admins exist doesn't "stick" across a redeploy/restart — it silently reappears as a fresh row (new id, default name/role) the next time `rbac` starts, since `seed.ts` only checks "does this email exist," not "was this deliberately removed." If that resurrection is ever unwanted, the fix would be gating the insert on "the `users` table is completely empty" instead of "this specific email is missing" — not implemented here, since the safety-net behavior was explicitly chosen to stay as-is.

- The frontend is wired to this — see the Frontend section above. `backend/shared-types` mirrors `frontend/src/types.ts` and is the contract both sides are expected to stay in sync with. `User.connectionIds` (alongside the pre-existing `AuthenticatedUser.connectionIds`, both from `rbac/src/lib/userDto.ts`) lets the Users & Roles drawer (`frontend/src/components/users/UserDrawer.tsx`) show and pre-check which cloud connections a Viewer can see, sending `accountConnectionIds` on `POST`/`PATCH /api/users` — only when the form's role is `viewer`; omitted for `admin` so promoting/demoting never touches existing assignments.
- `GET /api/vms`/`POST /api/vms/refresh` stream NDJSON (one `VmStreamFrame` per line — `shared-types`) instead of returning one combined JSON body, so the Inventory screen can show each provider/connection's VMs as soon as that connection's fetch settles rather than waiting for the slowest of all 5 (AWS alone can take up to 45s). The Aggregator's old `fetchAllVms` (`Promise.allSettled` + collect-after-the-fact, plus its local `FetchError` type) is gone, replaced by `fanout.ts`'s `fanOutVms(connections, forceRefresh, onResult)`, which invokes `onResult` the instant each connection's `fetchInstancesCached` call settles — success, stale-cache-fallback-with-error, or hard failure all "arrive" exactly once, `lock.ts` itself untouched. `routes/vms.ts` (`GET /vms`, `POST /vms/refresh`) calls `reply.hijack()` + writes raw NDJSON lines: a `{type:'start', connectionIds}` frame first (the full active-connection-id list, not just a count — lets consumers reconcile/prune), then one `{type:'connection', provider, connectionId, vms, error?}` frame per connection as it resolves, then `{type:'done', refreshedAt}`. The BFF (`bff/src/clients/aggregatorClient.ts`'s `streamAggregatorVms` + `bff/src/routes/vms.ts`'s `relay`/`scopeFrame`) relays this stream frame-by-frame rather than buffering it, role-scoping each `connection` frame's `vms` (empty array for a Viewer's inaccessible connection) while leaving `start`/`done` frames and a scoped-out connection's frame *existence* unscoped — same precedent as the pre-streaming route's unscoped `errors` array, so a Viewer still sees accurate overall refresh progress. `frontend/nginx.conf` has a dedicated `location /api/vms` (longer prefix than the general `/api/` block, wins automatically) with `proxy_buffering off`/`proxy_http_version 1.1`/`proxy_read_timeout 120s` — without it nginx's default buffered proxying would collect the whole chunked response before flushing it to the browser, silently defeating the streaming even though the origin streams correctly. Both `aggregator/src/routes/vms.ts` and `bff/src/routes/vms.ts` also call `reply.raw.socket?.setNoDelay(true)` right after `reply.hijack()` (Nagle's algorithm otherwise coalesces the small, frequent per-connection writes) and the aggregator writes a `{type:'ping'}` heartbeat frame (new `VmStreamFrame` variant, ignored by the BFF's scoping and by the frontend's `consumeVmStream`) every 1s while `fanOutVms` is still running, so any idle-timeout-based buffering intermediary between the origin and the browser gets more chances to flush during a slow real fetch — added after a real report of the stream arriving all-at-once in a Windows browser hitting this stack through WSL2's `localhost` port-forwarding relay (a known point where chunked responses can get buffered; verified the origin streams correctly via `curl` run *inside* the WSL2 VM, which bypasses that relay entirely). If a buffering intermediary does full-buffer-until-close rather than idle-based buffering, no app-level heartbeat fixes it — the workaround is bypassing the relay (hit the WSL2 VM's own IP — `ip -4 addr show eth0` — directly from the Windows browser instead of `localhost`) or switching WSL2 to mirrored networking mode (`.wslconfig`'s `[wsl2]\nnetworkingMode=mirrored`, Windows 11 22H2+/WSL ≥ 2.0.0).

## Versioning

Cirrus uses **lockstep semantic versioning** — one version number applies to all 10 first-party services at once (`bff`, `auth`, `rbac`, `aggregator`, `frontend`, and the 5 Go collectors), never independent per-service semver. This follows directly from the deployment shape: every service is always built and deployed together via one `docker-compose up -d --build`, and `backend/shared-types` is a hard cross-service contract, so there's never a scenario where "just the collectors" or "just the frontend" ship a different version than the rest.

- **Source of truth**: the root `VERSION` file (`/VERSION`, one line, e.g. `1.0.0`, git-tracked) — the simplest cross-language contract for a mixed Node+Go monorepo (no parsing, no new dependency). Everything else reads from it, directly or indirectly.
- **`scripts/bump-version.sh`** is the only thing that writes into the 7 `package.json` files' `"version"` field (`backend/package.json`, `backend/shared-types`, `backend/bff`, `backend/auth`, `backend/rbac`, `backend/aggregator`, `frontend`) — run with no argument to re-sync all 7 from the current `VERSION`, or with a version string argument (e.g. `./scripts/bump-version.sh 1.2.0`) to write that into `VERSION` first, then sync. Deliberately a hand-rolled shell script (using `node -e` for the actual JSON edit, not `sed`, to avoid corrupting formatting) rather than `changesets`/`lerna` — those solve independent-package versioning and registry-publish workflows, neither of which applies here (every `package.json` is `"private": true`, and lockstep is the whole point).
- **Go collectors** get the version stamped at build time via ldflags targeting a var inside the *shared* `internal-kit` package (module path `cirrus/collectorkit`), not duplicated per collector's `main.go`: `backend/collectors/internal-kit/server.go` (or its own tiny file) declares `var Version = "dev"`, and `HealthHandler` returns it in `/healthz`'s JSON body. Each of the 5 collector Dockerfiles' build stage takes a `CIRRUS_VERSION` build `ARG` (default `dev`) and appends `-X cirrus/collectorkit.Version=${CIRRUS_VERSION}` to the existing `-ldflags="-s -w"`. This works because ldflags' `-X importpath.Var=value` can target any package the final binary links in, and every collector's `go.mod` already `replace`s `cirrus/collectorkit` with the sibling `internal-kit` module — so one shared var, set once, backs all 5 binaries with zero `cmd/main.go` changes. `Version` defaults to `"dev"` so a build that skips the arg (a bare `go build`/`go test`) fails soft — an obviously-wrong value in `/healthz` — rather than crashing.
- **Node services** read their own already-shipped `package.json`'s `"version"` field at boot, not a separate env var — confirmed against each Dockerfile's final `run` stage, which already `COPY`s the service's own `package.json` in for `npm`/module-resolution reasons, so this is free. Each of `bff`/`auth`/`rbac`/`aggregator` has a tiny `src/version.ts` (`fileURLToPath(import.meta.url)` + `join('..', 'package.json')`, resolving correctly from both `src/` in dev and the compiled `dist/` in prod, since `tsc -b`'s output mirrors `src/` one level below the service root) exporting `version: string`; each `server.ts`'s `/health` route returns `{ status: 'ok', version }` instead of the old bare `{ status: 'ok' }`. Reading from `package.json` (rather than a `CIRRUS_VERSION` env var, which also exists — see below) means there's exactly one value that can drift, and the bump script is what keeps it in sync.
- **`docker-compose.yml`**: all 10 first-party services now carry an explicit `image: cirrus-<service>:${CIRRUS_VERSION:-dev}` alongside their existing `build:` block — Compose supports both together, so `docker compose build`/`up --build` still works fully offline (no registry), just now tags the result instead of leaving it at the implicit auto-named `:latest`. The 5 `collector-*` services additionally pass `build.args.CIRRUS_VERSION: ${CIRRUS_VERSION:-dev}` (the only 5 whose Dockerfile has a matching `ARG` — the other 5 read `package.json` instead, so wiring an unconsumed arg into their blocks too would look wired up but silently do nothing). `CIRRUS_VERSION` deliberately uses a **soft** `:-dev` default, not this repo's `${VAR:?message}` fail-fast convention for secrets (`INTERNAL_SHARED_SECRET`/`COOKIE_SECRET`/`POSTGRES_PASSWORD`/`VAULT_TOKEN`) — a missing version string has no security implication and shouldn't block a contributor's local `docker compose up` the way a missing secret should. `docker-compose.prod.yml`/`docker-compose.dev.yml` need no changes — neither overlay touches `image:`/`build:`.
- **`.env.example`**/the real `.env` both carry `CIRRUS_VERSION=1.0.0`. It's read by `docker-compose.yml` at `up`/`build` time and must be bumped by hand alongside the root `VERSION` file on every release — the bump script only touches git-tracked files (`VERSION` + the 7 `package.json`s), deliberately never the gitignored `.env`.
- **Frontend UI display**: `frontend/vite.config.ts` reads `frontend/package.json`'s version at build time (via `node:fs`, since the config runs in Node, not the browser) and exposes it to the bundle through Vite's `define` as a global `__APP_VERSION__` (typed via a new `frontend/src/vite-env.d.ts`, the first custom build-time constant this repo exposes to TypeScript — previously the only `import.meta.env` usage anywhere was Vite's own built-in `DEV` flag). Rendered in two places so it's visible regardless of role or auth state: the bottom of `Sidebar.tsx`'s existing user-profile row (small, muted, centered — visible on every protected route for both Admin and Viewer) and near the existing muted footnote at the bottom of `LoginScreen.tsx`'s card.
- **Health endpoints**: `GET /health` (bff/auth/rbac/aggregator) and `GET /healthz` (all 5 collectors) now return `{"status":"ok","version":"1.0.0"}` instead of a bare status — the version field is additive, so it doesn't affect either healthcheck mechanism (`docker-compose.yml`'s Node healthchecks only check HTTP status via `fetch(...).then(r=>r.ok)`, and the collectors' `wget --spider` only checks reachability). Confirmed live: built `collector-aws`'s image with `--build-arg CIRRUS_VERSION=1.0.0` and curled `/healthz` → `{"status":"ok","version":"1.0.0"}`, proving the ldflags injection actually reaches the shared `collectorkit.Version` var.
- **Release flow**: decide the new version → `./scripts/bump-version.sh X.Y.Z` → review the diff → commit (`chore: bump version to X.Y.Z`, bullet-point body, no scope since it's repo-wide, per this file's Git conventions below) → `git tag -a vX.Y.Z -m "vX.Y.Z"` on that commit → bump `CIRRUS_VERSION` in the real `.env` to match → `docker compose build`/`up -d --build` for a local deploy → push the commit and tag yourself (never automated) — pushing the tag is also what triggers the GHCR publish below. The bump/commit/tag steps themselves stay manual (no CI drives them); only the build+push-to-registry step is automated, via the workflow described next.
- **`.github/workflows/publish-images.yml`** builds and pushes all 10 first-party service images to GitHub Container Registry — this repo's first GitHub Actions workflow, scoped narrowly to image publishing (the broader P3 lint/test/build-check CI item is still unbuilt, see `TODO.md`). Triggers on a `vX.Y.Z` tag push (the same release flow above) or manually via `workflow_dispatch`. A single job with a 10-way matrix (one per service) checks out the repo, derives the version straight from the committed `VERSION` file (cross-checked against the pushed tag name when triggered by a tag push, so tagging before running `bump-version.sh` fails loudly instead of silently publishing a stale version), and runs `docker/build-push-action` — the 5 collectors additionally get `CIRRUS_VERSION` as a build arg, mirroring `docker-compose.yml`'s own choice not to wire it into the other 5 services. Images publish as `ghcr.io/hafizhasyari/cirrus/<service>` (e.g. `ghcr.io/hafizhasyari/cirrus/bff`), tagged with both the release version and `latest` — a distinct namespace from the local `cirrus-<service>` names `docker-compose.yml` uses, no collision. Requires an explicit top-level `permissions: { contents: read, packages: write }` in the workflow, since this repo's Actions default token permission is read-only. The repo and every published package are public — GHCR packages default to **private** on first publish regardless of the repo's own visibility, and GitHub exposes no API to change that, so each of the 10 packages needed one manual one-time UI step (package settings → Danger Zone → Change visibility → Public) after their first publish.
- **Before making the repo public, its git history was rewritten** (`git filter-repo`, run against a fresh mirror clone, then force-pushed) to remove an early commit pair's mockup/design-phase data — a short-lived `frontend/src/data/mockData.ts` (added and removed same-day, long before the real backend was wired up) whose placeholder names/emails/cloud-account identifiers weren't confidently distinguishable from real ones, plus a couple of unrelated real-infrastructure specifics (a real IP address example, a literal exploit-shaped URL example, a personal email) that had crept into `CLAUDE.md`'s own prose over time. Commit *author* metadata (name/email on every commit) was deliberately left untouched — a separate, accepted decision from redacting file content. This is the second history rewrite in this repo's life, after the Conventional-Commits `filter-branch --msg-filter` pass noted below.

## PRD.md

`PRD.md` is the single source of truth for this project — **Cirrus**, a Cloud VM Inventory Dashboard. Status: Approved. It is written in Bahasa Indonesia prose with English used for role names, table headers, and UI labels (this mixed convention is intentional — keep it when editing).

Key facts to know before making changes to the PRD or (later) implementing against it:

- **What it is**: an internal, read-only dashboard that aggregates VM inventory across the company's own accounts on 5 cloud providers (AWS, GCP, Alibaba Cloud, OCI, Biznet Gio Cloud) — not a multi-tenant SaaS. Avoid "customer" framing when describing cross-account auth; use "akun cloud yang didaftarkan" / "tim pemilik akun" instead.
- **Current MVP scope (§4)**: inventory list + filter/search + RBAC/SSO only. Cost/billing was deliberately cut from the MVP and moved to §10 Roadmap (with the per-provider cost-API research preserved there so it isn't lost) — don't reintroduce cost UI/flows into MVP sections (§2–§9).
- **Roles (§3)**: exactly 2 — `Admin` (manage users/roles, manage cloud account connections, view all data) and `Viewer` (view inventory for assigned accounts/projects only).
- **Auth**: Microsoft Entra ID (Microsoft 365) via OIDC, single-tenant. Identity key is `oid`+`tid` (never `email`, which is mutable).
- **Architecture (§7)**: microservices, Docker for dev / Kubernetes for prod. Frontend SPA → API Gateway/BFF → Auth Service + RBAC Service → Inventory Aggregator → 5 Provider Collectors (one per cloud, each exposing a uniform `GET /instances`). Redis caches fetch results (TTL 2–5 min, with a cache-stampede lock); PostgreSQL holds app metadata only (never live-pulled VM data).
- **Per-provider credential model (§7.3)** — deliberately different per provider, verified against current docs, don't default back to "just use an API key" for all of them:
  - GCP: Workload Identity Federation — no static secret stored at all.
  - AWS, Alibaba Cloud, OCI & Biznet Gio Cloud: static per-account credentials (IAM User Access Key / RAM User AccessKey / API Signing Key / `x-token`) in Vault KV v2 — AWS and Alibaba Cloud both deliberately moved off cross-account role assumption to this per-account model (simpler per-account setup, no hub/trust-policy, at the cost of a long-lived key vs. each provider's own recommended short-lived role assumption).
- **Tech stack (§8)**: React+TypeScript+Vite frontend; Go (using `errgroup` for collector fan-out) for Provider Collectors; Node.js/TypeScript for BFF/Aggregator/RBAC; PostgreSQL + Redis; HashiCorp Vault (KV v2); Helm umbrella chart (one subchart per microservice) for Kubernetes deploy.
